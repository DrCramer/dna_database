# dna_database — анализ ДНК-профилей

Веб-приложение для хранения ДНК-профилей, работы с задачами лаборатории, поиска совпадений и анализа контаминации. Интерфейс написан на React, API — на Express. PostgreSQL хранит данные, Redis используется приложением как кэш. Проект запускается через Docker Compose.

> Репозиторий содержит исходный код и схему пустой базы. Реальные ДНК-профили, дампы, ключ шифрования и рабочие пароли в GitHub не публикуются.

## Возможности

- Учёт пользователей, организаций и отделов с ролевым доступом.
- Импорт, просмотр и поиск ДНК-профилей; экспорт результатов.
- Работа с задачами, мастер-массивами и профилями сотрудников.
- Анализ совпадений и журнал поиска контаминации.
- REST API с авторизацией через JWT и проверка состояния `/health`.

## Требования

- Linux с Docker Engine и Docker Compose v2 (`docker compose`).
- Git, Bash и OpenSSL.
- Свободные порты `3001` для сайта и `5433` для локального доступа к PostgreSQL. Порт `3000` на хосте не используется.
- Достаточно места для PostgreSQL и резервных копий в каталоге проекта.

## Разработка интерфейса

Установите зависимости вместе с инструментами сборки и выполните проверки:

```bash
npm ci --include=dev
npm run check:ui
npm run check:imports
npm test
npm run build
```

Единая точка подключения CSS — `frontend/src/styles/index.css`. Общие размеры,
цвета и отступы задаются в `styles/base/variables.css`, кнопки, поля, карточки,
таблицы и модальные окна — в `styles/components/`. Все рабочие маршруты используют
`PageShell` шириной до 1400 px; `/analysis` использует вариант `fluid` без ограничения
ширины. Компоненты не импортируют собственные CSS: специфичные стили подключаются
через общий манифест и ограничиваются областью своего компонента.

`check:ui` проверяет импорты, владельцев CSS-селекторов, уникальность анимаций,
существование токенов и отсутствие ограничения ширины анализа. Эта проверка также
выполняется при сборке Docker-образа. Подробности ревизии, исключения и результаты
проверки страниц описаны в [отчёте по UI](docs/UI_REVISION.md).

`check:imports` проверяет относительные ссылки во frontend, backend, тестах
и скриптах, включая модули вне основного bundle. Проверка включена в Docker-сборку.
Байесовский UI находится в `frontend/src/components/Analysis/Bayesian/`,
серверные сервисы сгруппированы по доменам в `src/services/`.
Подробности: [архитектурный рефакторинг](docs/REFACTOR_PHASE3.md),
[политики доступа, шифрование и ошибки API](docs/REFACTOR_PHASE4.md).

## Быстрая установка с пустой базой

```bash
git clone https://github.com/DrCramer/dna_database.git
cd dna_database
./scripts/install.sh
```

Скрипт создаёт `.env` со случайными паролями, 32-байтовый `config/encryption.key`, локальные каталоги данных, собирает образ, загружает [схему пустой БД](database/schema.sql) и справочник STR-локусов, создаёт администратора и запускает сервисы. Если база уже содержит пользователей, скрипт их не меняет.

Схема и справочник загружаются одной транзакцией. Для каждого отделения сразу
создаётся мастер-массив. Установщик проверяет полное состояние `/health`,
включая сохранность данных. При повторном запуске пароли, ключ и данные
сохраняются. Неполный bootstrap прежней пустой установки исправляется миграцией
**030** с предварительным SQL-дампом; исторические миграции импорта автоматически
не применяются.

[Отчёт о проверке установки с нуля, API и перезапусков](docs/INSTALLATION_VERIFICATION.md).

По умолчанию сайт доступен только на самом сервере: **http://localhost:3001/**. Имя администратора — `admin`, пароль находится в `ADMIN_PASSWORD` файла `.env`. Файл доступен только владельцу (`chmod 600`). После входа смените пароль администратора через интерфейс.

Проверка:

```bash
docker compose ps
curl -f http://localhost:3001/health
```

Для доступа из локальной сети укажите адрес сервера до первой установки:

```bash
WEB_BIND_IP=192.168.1.16 FRONTEND_URL=http://192.168.1.16:3001 ./scripts/install.sh
```

Замените `192.168.1.16` на IP своего сервера. Если `.env` уже создан, отредактируйте в нём `WEB_BIND_IP`, `FRONTEND_URL` и `CORS_ORIGIN`, затем выполните `docker compose up -d --force-recreate web`. Для другого порта измените также `WEB_PORT` и порт в URL. HTTP-развёртывание рассчитано на доверенную сеть; для доступа через интернет настройте HTTPS на обратном прокси.

## Настройки и файлы данных

[.env.example](.env.example) перечисляет основные параметры. `scripts/install.sh` генерирует рабочий `.env` автоматически. При переносе установки используйте **существующий** `.env`, а не новый пароль для уже созданного кластера PostgreSQL.

| Назначение | Путь внутри каталога проекта |
| --- | --- |
| PostgreSQL | `runtime/postgres/` |
| Redis | `runtime/redis/` |
| Загруженные файлы | `runtime/uploads/` |
| Экспорт | `runtime/exports/` |
| Резервные копии | `runtime/backups/` |
| Логи приложения | `logs/` |
| Ключ шифрования | `config/encryption.key` |
| Настройки и пароли | `.env` |

Все Docker volume в [docker-compose.yml](docker-compose.yml) — bind mount внутри проекта. `runtime/`, `.env`, ключ, логи и дампы исключены из Git и из контекста сборки образа. Храните резервную копию `.env` и ключа отдельно: без прежнего ключа ранее зашифрованные данные могут стать недоступны.

`scripts/prepare-runtime.sh`, вызываемый установкой и обновлением, сохраняет
владельца файлов на хосте и даёт группе `node` доступ к каталогам web. Это позволяет
устанавливать проект от `root` или пользователя с другим UID; web продолжает
работать от `node`. `.env` имеет права `600`, ключ — `640` с группой `node`.
Если постоянный ключ недоступен или повреждён, production backend останавливается
с понятной ошибкой; временный ключ вместо него не используется.

Основные команды:

```bash
docker compose ps
docker compose logs --tail=100 web
docker compose logs --tail=100 db
docker compose up -d
docker compose down
```

`docker compose down` останавливает контейнеры и сохраняет каталоги `runtime/`. Не удаляйте их при обновлении.

## Обновление через GitHub

Если уже выполнена новая установка и в логах есть `parameter_key does not exist`
или отсутствуют мастер-массивы отделений, сохраните существующие `.env`, ключ и
`runtime/`, получите исправление и повторите установщик:

```bash
git pull --ff-only origin main
./scripts/install.sh
```

Установщик переиспользует эту БД, создаёт резервную копию перед ремонтом 030 и
сохраняет существующие учётные записи. Для обновления старых установок до 027–029
сначала следуйте инструкциям соответствующих миграций ниже.

Как и в `dna_base`, обновление выполняется из каталога проекта. Сначала проверьте локальные изменения:

```bash
cd ~/dna_database
git status --short
git branch --show-current
```

Для обычного обновления используйте скрипт:

```bash
./scripts/update_server.sh
```

Он создаёт SQL-дамп в `runtime/backups/`, выполняет `git pull --ff-only origin main`, пересобирает контейнеры и ждёт успешной проверки здоровья. `.env`, ключ, PostgreSQL, загрузки и экспорт остаются на месте. Скрипт распознаёт миграции 031–036 и применяет их после резервной копии: 031 добавляет таблицы справочников, 032 включает год в ключи генетических профилей, 033 добавляет Фамилию И.О. и делает почту необязательной, 034 хранит снимки расчётов IDENT/TRIO, 035 добавляет отзыв и ротацию refresh-токенов и корректный часовой пояс срока сессии, 036 разделяет уникальность номеров профилей по организации и отделению. При других изменениях схемы или миграций скрипт остановится перед запуском нового кода: сначала изучите инструкции к соответствующему релизу и примените нужную миграцию к копии БД. Автоматическое применение исторических SQL-файлов не выполняется.

Если прежняя версия скрипта остановилась после `git pull` из-за добавления миграций 031–036, повторите `./scripts/update_server.sh`. Обновлённый скрипт проверит наличие таблиц, индексов и полей пользователей даже при отсутствии новых изменений Git и применит недостающую миграцию после резервной копии.

Те же шаги вручную:

```bash
mkdir -p runtime/backups
docker compose exec -T db pg_dump -U dna_user -d dna_analysis \
  > "runtime/backups/dna_analysis_$(date -u +%Y%m%d_%H%M%S).sql"
git pull --ff-only origin main
./scripts/install.sh # проверит схему, применит недостающие миграции и сохранит данные
docker compose ps
curl -f http://localhost:3001/health
```

Для установки с `WEB_BIND_IP`, отличным от `127.0.0.1` или `0.0.0.0`, используйте этот IP вместо `localhost` в проверке `curl`. Не выполняйте `git reset --hard` для решения конфликта локальных изменений: сначала сохраните их. Если Git сообщает о неправильном владельце каталога после копирования через `sudo`, верните каталог своему пользователю и запускайте Git без `sudo`.

## Резервная копия и перенос установки

Резервная копия БД:

```bash
mkdir -p runtime/backups
docker compose exec -T db pg_dump -U dna_user -d dna_analysis \
  > "runtime/backups/dna_analysis_$(date -u +%Y%m%d_%H%M%S).sql"
```

Для восстановления на новом сервере скопируйте `.env`, `config/encryption.key` и нужные файлы из `runtime/uploads/` защищённым способом. Затем запустите пустой PostgreSQL и импортируйте дамп **до** запуска веб-приложения:

```bash
docker compose up -d db redis
docker compose exec -T db psql -U dna_user -d dna_analysis -v ON_ERROR_STOP=1 \
  < /путь/к/резервной_копии.sql
docker compose up -d --build web
```

Импорт рассчитан на пустую базу. Не применяйте его поверх рабочей БД: сначала сделайте копию и проверьте выбранный файл. При переносе готовой установки можно перенести весь `runtime/` вместе с `.env` и ключом, сохранив права и версию PostgreSQL 15.

## API

API доступен по адресу сайта с префиксом `/api`. Например, для локальной установки:

```bash
export API_URL='http://localhost:3001'
curl "$API_URL/health"
```

`/health` доступен без авторизации. Для остальных примеров сначала получите JWT:

```bash
curl -sS -X POST "$API_URL/api/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"<логин>","password":"<пароль>"}'
```

Ответ содержит `data.accessToken`. Скопируйте его в переменную `TOKEN`, а ID
нужного отдела возьмите из `data.user.accessible_departments` или ответа
`GET /api/auth/me`:

```bash
export TOKEN='<accessToken>'
export DEPARTMENT_ID='<UUID активного отдела>'
curl -sS "$API_URL/api/auth/me" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Active-Department-Id: $DEPARTMENT_ID"
```

Для запросов с данными используйте оба заголовка: JWT и `X-Active-Department-Id`.
Отдел должен быть доступен пользователю; права API ограничивают выдачу профилей
активным отделом и ролью. Передавайте токен именно как `Bearer` и не публикуйте его.

Основные маршруты:

| Действие | Метод и путь |
| --- | --- |
| Текущий пользователь и доступные отделы | `GET /api/auth/me` |
| Доступные профили с пагинацией | `GET /api/profiles/accessible?limit=100&offset=0` |
| Активные задачи пользователя | `GET /api/tasks/my-active` |
| Профили задачи | `GET /api/tasks/{taskId}/profiles` |
| Сравнить два профиля по UUID | `POST /api/analysis/compare` |
| Поиск совпадений в задаче или мастер-массиве | `POST /api/genotype-analysis/task-search` |
| Предварительно проверить Excel | `POST /api/profiles/upload/preview` (multipart) |
| Загрузить Excel в задачу | `POST /api/profiles/upload` (multipart) |

Пример сравнения двух профилей:

```bash
curl -sS -X POST "$API_URL/api/analysis/compare" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Active-Department-Id: $DEPARTMENT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"profile1Id":"<UUID профиля 1>","profile2Id":"<UUID профиля 2>","options":{"minNumericMatches":15,"enableBayesianAnalysis":true}}'
```

Пример поиска профилей в задаче:

```bash
curl -sS -X POST "$API_URL/api/genotype-analysis/task-search" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Active-Department-Id: $DEPARTMENT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"taskId":"<UUID задачи>","searchMode":"task","minMatches":15,"ignoredLoci":[],"comparisonAlgorithm":"standard"}'
```

Для поиска по мастер-массиву задайте `"searchMode":"master_array"`. Ответ — JSON
с результатами и статистикой; UUID задачи можно получить через `GET /api/tasks`.

Excel отправляется как `multipart/form-data` с полем `file`. Для импорта в задачу
передайте поле `taskId` (UUID); сервер проверит доступ и право загрузки. Пример
предварительной проверки:

```bash
curl -sS -X POST "$API_URL/api/profiles/upload/preview" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Active-Department-Id: $DEPARTMENT_ID" \
  -F 'file=@profiles.xlsx' \
  -F 'taskId=<UUID задачи>'
```

Успешный ответ обычно содержит `success: true`. Ошибки `/api` возвращают HTTP
статус и общий JSON: `success: false`, `message`, `code`, `status`, `requestId`,
`timestamp`. Поле `error` сохранено для совместимости и может быть строкой
или объектом. `requestId` также доступен в заголовке `X-Request-Id`; используйте
его для поиска ошибки в серверных логах. В production ответы 5xx скрывают
внутренние подробности. Частые статусы: `400` — некорректный запрос или файл,
`401` — отсутствующий/истёкший токен, `403` — нет доступа к отделу, задаче или
профилю. Подробности форматов импорта и интеграции доступны в разделах выше и
в [документации legacy API](docs/LEGACY_PROFILE_ACCESS.md).

## Форматы импорта ДНК-профилей

Если Excel не прошёл валидацию, страница загрузки показывает конкретные причины,
номера строк/ячеек и подсказки исправления. Например, `для импорта.xlsx` нужно
переименовать в `для_импорта.xlsx`: пробелы в имени готового Excel не допускаются.
Предупреждения отображаются отдельно и сами по себе не блокируют импорт.
Столбец «Год» поддерживается в формате ЧС и не считается неизвестным.

Загрузка по умолчанию разрешена только в доступную задачу со статусом **«В работе»**
в активном отделении. При принятии задача автоматически выбирается для работы.
На странице **«Загрузка профилей»** проверьте поле **«Куда загрузить профили»**:
там можно выбрать доступную задачу. Если задача «В работе» всего одна, она выбирается
автоматически; если задач несколько, выберите нужную.
В меню **«Пользователи» → создание/редактирование → «Права загрузки ДНК-профилей»**
администратор отдельно разрешает загрузку в задачу и без задачи. Загрузка без
задачи по умолчанию выключена для всех пользователей, включая администратора.
Даже при разрешённой загрузке без задачи нужно явно выбрать **«Без задачи — отдельная
загрузка»**. Отсутствие выбранной задачи само по себе больше не разрешает импорт.
API проверяет права и `taskId`; настройки прав из тела запроса загрузки не учитываются.
Для импорта в задачу передавайте `taskId` (UUID; также поддерживается `task_id`),
для разрешённого импорта без задачи — `uploadTarget=without_task`.
Предварительный просмотр и результат импорта возвращают `taskId`, а сохранение
проверяет привязку в транзакции. [Восстановление загрузки вне задачи](docs/TASK_UPLOAD_BINDING.md).

В установках до настройки прав загрузки требуется миграция **028** после 027.
В текущей версии после них также применяются **029** и **032** (см. ниже).
[Настройка прав и команды обновления](docs/UPLOAD_PERMISSIONS.md).

Формат выбирается по **активному отделению**. Для «Генетические экспертизы»:

```text
Объект | Год  | TH01 | D5S818 | D21S11
110-1  | 2026 | 7,9  | 11,12  | 29,30
```

Первый столбец — «Объект», второй — «Год», далее идут минимум три поддерживаемых локуса.
Пара «Год + Объект» уникальна в рамках пользователя и отделения, поэтому номер
может повторяться в разных годах. Порядок локусов может отличаться; их имена
нормализуются по справочнику. Для «ЧС» сохранён прежний формат с годом,
привозом и номерами образцов. API preview/upload учитывают
`X-Active-Department-Id` и проверяют доступ пользователя.

Для установок до genetic import сначала нужны **027**, **028**, затем **029**;
для годового ключа генетического объекта нужна **032**. Обновляющий скрипт
применит её автоматически после резервного копирования.
Формат, проверка дубликатов и тесты:
[документация импорта](docs/GENETIC_IMPORT.md).

Существующий конвертер также поддерживает [NGS ASTR+ (Result / Detail)](docs/NGS_ASTR_CONVERTER.md): подтверждение номера объекта, проверку QC и просмотр исходных данных в конвертере.

Для старых `.xlsx`/`.xls` доступен [Конвертер Excel](docs/GENETIC_EXCEL_CONVERTER.md):
выбор листов и колонок, нормализация, слияние нескольких исследований, ручная
проверка неоднозначностей и передача в штатную загрузку с активной задачей.

В конвертере и штатном импорте локус **SRY** принимает текстовый сигнал `SRY` и прежние числовые значения. Регистр сигнала нормализуется, одиночное значение не дублируется. Флажок **«Скрывать пустые локусы в Excel»** скрывает столбцы без данных у всех объектов; их можно снова показать в Excel. Нормализованный Excel содержит ровно один лист **Импорт**, без скрытых или диагностических листов. Половые локусы стоят в конце. Имя файла берётся из номеров объектов и года: `250-1`, `250-2`, 2026 → `250-2026.xlsx`. Диагностика доступна в конвертере, а панель при необходимости выбирается при загрузке.

## Генетические панели и номера объектов

[Интеллектуальная проверка аллелей](docs/ALLELE_REFERENCE_VALIDATION.md) сравнивает варианты записи с точными аллельными лестницами, известными STR-вариантами и реальными популяционными частотами. Справочники импортируются через **Настройки → Генетические справочники**, версионируются и явно связываются с панелями. Подготовлен проверенный JSON PowerPlex Fusion TMD039 7/20; перед подключением подтвердите соответствие используемой системе. Неоднозначные изменения требуют решения оператора. Миграция **031** добавляет справочные таблицы с сохранением существующих профилей.

В отделении «Генетические экспертизы» для объекта `258-11x` сохраняются
`sample_name=258` (№ Экспертизы) и `internal_number=258-11x` (полный № Объекта).
Несколько объектов одной экспертизы разрешены; дубликаты определяются по году
и полному номеру объекта. Поле `import_number` отображается как **ФИО**, в ЧС — **Привоз**.

В меню **Настройки → Панели** можно создать панель с упорядоченным набором
локусов. При genetic upload панель выбирается необязательно. Состав и порядок
локусов проверяются по существующему каталогу; реальные панели не предзаполнены.
Анализ показывает все локусы профилей и использует порядок назначенных панелей.

Перед запуском новой версии на существующей БД примените **029** и **032**,
предварительно создав SQL-дамп. [Порядок обновления, API и отчёт по 20 пунктам](docs/GENETIC_PANELS_AND_ANALYSIS.md).

## Производительность поиска дубликатов

Поиск внутри задачи, в мастер-массиве и задачах отдела автоматически использует рабочие потоки Node.js при 10 000 и более потенциальных сравнений. Разбор аллелей для `duplicate_v5` кэшируется на время поиска; подробности формируются для найденных совпадений. Пороги, направленность сравнения, порядок результатов и полный экспорт сохраняются.

По умолчанию используются до **4 потоков**, с ограничением по доступным CPU и Docker CPU quota. Чтобы изменить максимум, добавьте в `.env`:

```dotenv
GENOTYPE_SEARCH_WORKERS=4
```

Применить настройку: `docker compose up -d --no-deps web`. На сервере с одним доступным CPU расчёт использует один рабочий поток; HTTP-сервер при этом остаётся доступным. Несколько тяжёлых поисков задач выполняются по очереди, чтобы не создавать по набору потоков на каждого пользователя. При отключении клиента или превышении 10 минут потоки освобождаются. В статистике API поиска доступны `mode` и `workerCount`.

Для замера на 3000 синтетических профилей без доступа к БД:

```bash
docker compose exec web node scripts/benchmark-task-search.js 3000 duplicate_v5
docker compose exec web node scripts/benchmark-task-search.js 3000 duplicate_v5 sequential
```

Сравните время `durationMs` и `resultHash`: хеш результатов должен совпасть. Фактическое ускорение зависит от CPU, числа локусов, порогов и количества найденных совпадений.

### Критерии сравнения и одиночная запись в XLSX

Стандартный поиск считает `10` и `10,10` эквивалентными, но не считает их точным совпадением с `10,11` или смесью. В поиске дублей v5 обязательны одновременно минимальный балл, процент и число сравненных локусов. Поиск контаминации соблюдает минимум совпадений; критерии внутри задачи и между задачами сотрудников согласованы. [Описание критериев и доступа](docs/GENOTYPE_COMPARISON.md).

В Excel конвертера, мастер-массива и дубликатов одинаковая пара аллелей DYS391, зарегистрированных RS-маркеров и DXS6795 выводится одним значением (`10,10` → `10`). Разные аллели, смеси и неизвестные значения сохраняются; исходные профили в БД не меняются.

## Экспорт мастер-массива (администратор)

Для выгрузки самого мастер-массива администратор открывает **Система → Экспорт мастер-массива** (`/admin/master-array-export`). Выберите доступный массив, все активные профили или фильтры по году/номеру, затем нажмите **Проверить выгрузку**. Скачивание использует весь серверный результат, а не страницу таблицы. Полученный XLSX содержит один лист **Импорт** и подходит для штатной загрузки в соответствующее отделение. Экспорт не изменяет мастер-массив.

При неполных исторических данных полная выгрузка блокируется. Доступны CSV-отчёт с причинами и отдельный режим **только пригодные**, требующий подтверждения исключений. Генотипы, отсутствующий год и номера не исправляются и не дополняются автоматически. Подробности, ограничения, mapping ЧС и API: [административный экспорт мастер-массива](docs/MASTER_ARRAY_EXPORT.md).

## Экспорт дубликатов в Excel

На странице **Анализ генотипов** выполните поиск внутри задачи, в мастер-массиве, в задачах отдела или полный поиск. Откройте **Результаты сравнения** и нажмите **Экспорт дубликатов в Excel**. Кнопка также доступна во вкладке **История** после выбора результата недавнего поиска.

Кнопка видна даже до поиска: пока нет доступных результатов, она неактивна и рядом указана причина. Поиск контаминаций сам по себе не создаёт отчёт дубликатов. Для старой истории, результатов старше 30 минут или после перезапуска приложения необходимо повторить поиск.

В окне экспорта можно выбрать все найденные пары либо группу эталона, все локусы либо отображаемые, включить эталоны, подсветку, подробные сравнения и сведения об анализе. Лист **Сравнения** содержит `Роль`, `Объект`, `Эталон`, `Совпавшие локусы` и локусы. В числе совпавших учитываются только полностью совпавшие локусы с зелёной подсветкой; частичные совпадения в это число не входят.

Повторные пары, включая обратные A–B / B–A и совпадения из нескольких поисков, выгружаются один раз. На листе **Сравнения** эталон указан один раз перед своей группой совпадений; на листе **Профили** каждая запись представлена один раз. Разные записи с одинаковым номером (например, за разные годы) сохраняются отдельно. При выборе группы эталона сохраняется направление сравнения с выбранным эталоном.

После обновления проекта с GitHub запустите `./scripts/update_server.sh`: скрипт создаёт резервную копию БД, применяет необходимые миграции и пересобирает приложение. Если вкладка браузера была открыта во время обновления, перезагрузите её с помощью **Ctrl+F5**.

## Ограничения текущей версии

- Поиск дубликатов по номеру воинской части отвечает `501`: в текущей схеме нет этого поля. Другие маршруты аналитики работают с имеющимися данными.
- Схема `database/schema.sql` — проверенный снимок для новой пустой установки. Исторический `database/init.sql` и файлы `database/migrations/` не запускайте поверх неё без проверки; установщик использует `schema.sql`.
- Публичный репозиторий не содержит лабораторных данных. После установки база пуста, кроме администратора, организации, отделов и справочника STR-локусов.


## Фамилия И.О. и создание пользователей

В меню **Пользователи → Создать пользователя** или **Редактировать** укажите

## GeneMapper TXT

Файлы `.txt` GeneMapper можно выбрать прямо в **Загрузке профилей** либо в
**Конвертере генетических профилей**. XLSX готовится автоматически, сохраняет имя
исходного TXT и скачивается по нажатию кнопки. Несколько TXT дают отдельные XLSX
и общий ZIP. Подтвердите год и проверьте исключённые образцы и предупреждения;
затем передайте готовый файл в обычный импорт с выбором задачи.

Поддерживаются пять аллельных колонок, микроаллели, гомозиготы, AMEL, Y и Y-InDel.
Принимается также сокращённый TAB-формат `Sample Name`, `Marker`, `Allele 1`,
`Allele 2` (до `Allele 5`) без `Sample Type`, `Panel` и `Status`. Если `Sample Type`
отсутствует, обычные образцы определяются по имени; известные служебные имена
исключаются. Пустой или неизвестный тип в существующей колонке требует проверки.
Дата `YYYYMMDD` в имени TXT используется как подсказка года; год нужно подтвердить.
Лестницы, контроли и пустые образцы исключаются с отчётом. В ЧС перед подготовкой
нужно заполнить номера в в/ч и привоза. Конвертация не сохраняет ДНК-профили в БД.
[Правила, API, ограничения и результаты проверки трёх файлов](docs/GENEMAPPER_TXT.md).

## Вероятность: IDENT / TRIO

В отделении «Генетические экспертизы» в верхнем меню доступна страница
`/probability`. Источники участников — разрешённые профили БД, внешний GeneMapper
TXT и ручная копия. TXT загружаются в общий блок один раз; образцы из одного
или нескольких файлов выбираются карточками с поиском, именем файла и числом
локусов. В TRIO сначала выберите участника, затем назначьте ему образец.
Повторная загрузка того же файла не создаёт дублей в списке. Ручной ввод и поиск
в БД свёрнуты у каждого участника. IDENT принимает один генотип с двумя
аллельными колонками; TRIO — неоспариваемого родителя, ребёнка и оспариваемого
родителя, в том числе из разных форезов. Для проверки TRIO показаны предполагаемые
отцовские аллели ребёнка, включая неоднозначные варианты.
Можно смешивать источники, отключать локусы, сохранять
неизменяемые снимки и выгружать XLSX / единый PNG для Word.
AMEL и неаутосомные маркеры всегда исключены. Выбора панели нет.
Половые маркеры скрыты из рабочей таблицы. SE33, LPL, F13A01, F13B и FESFPS
учитываются по расчётным строкам и частотам исходной книги. Результат виден справа;
отчёт с итогами и вариантами I/II подготовлен для ширины A4 180 мм. Локусы в
обоих вариантах стоят на одинаковых строках в порядке книги; отчёт выгружается
целиком, без страниц. Кнопка экспорта — «Выгрузить в формате XLSX».
Кнопка «Формулы» открывает справку с дробями; IDENT/TRIO оформлены вкладками.
По умолчанию в расчёт включаются только локусы с генотипами всех участников.
Явный выбор флажков сохраняется; пустой локус, включённый вручную, блокирует
расчёт. Это же правило действует в API при отсутствии `includedLoci`.
При загрузке TXT одиночная числовая аллель аутосомного STR дублируется для
представления гомозиготы (`12` → `12,12`, `9.3` → `9.3,9.3`), включая отчёты.
Исходная запись сохраняется в данных источника; половые локусы и SNP не дублируются.

- [Инструкция и формулы](docs/probability-user-guide.md).
- [Аудит исходной XLSM, контрольные числа и расхождения](docs/probability-excel-audit.md).
- Частоты: отдельная версия FREQ из предоставленной Probability 2.5.1 А29+.
- По решению пользователя совпадения TRIO используют **1−μ**, хотя ячейки
  TRIO_AN исходной книги используют 1. Это намеренное изменение модели.
- Пересчёт контрольных книг выполнен в **LibreOffice Calc**, а сверка в Microsoft
  Excel остаётся незавершённой. В одном многолокусном TRIO сохранено различие
  последнего печатного процентного разряда; оно описано в аудите.

Для установки и обновления добавлена идемпотентная миграция
`database/migrations/034_probability_calculations.sql`. Штатные `install.sh`
и `update_server.sh` применяют её до запуска новой версии; сохранение ключа
`config/encryption.key` обязательно для чтения AES-256-GCM снимков. Новых
секретов в `.env` для модуля не требуется. Исходные профили не перезаписываются.

API требует Bearer JWT, `X-Active-Department-Id` и прав в выбранном отделении:

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/probability/configuration` | Версия частот и формул, роли и список локусов |
| `GET /api/probability/profile-search?q=...` | Поиск доступных профилей |
| `GET /api/probability/profiles/:id` | Полный генотип, метаданные и sourceDigest |
| `POST /api/probability/txt/preview` | Multipart `files`, образцы и подписанный proof |
| `POST /api/probability/calculate` | Серверный расчёт без сохранения |
| `POST /api/probability/calculations` | Повторная проверка источников и сохранение снимка |
| `GET /api/probability/calculations` | До 100 последних собственных снимков |
| `GET /api/probability/calculations/:id` | Неизменённый сохранённый результат |
| `POST /api/probability/export` | XLSX текущего серверного расчёта |
| `GET /api/probability/calculations/:id/export?format=xlsx` | XLSX сохранённого снимка |
| `GET /api/probability/calculations/:id/export?format=report` | Подтверждённые данные печатного блока для клиентского PNG |

Пример тела для IDENT с одним генотипом из TXT (proof берётся из предпросмотра):

```json
{
  "mode": "IDENT",
  "includedLoci": ["TH01", "D1S1656"],
  "participants": [
    {"role": "object", "sourceType": "txt", "proof": "PROOF-ИЗ-ПРЕДПРОСМОТРА"}
  ]
}
```

Для TRIO роли: `mother`, `child`, `father`; для каждой можно отдельно получить
proof из своего TXT. В строках результата `paternalAlleles` содержит варианты
ребёнка, совместимые с оспариваемым родителем; `paternalAllelesAmbiguous` отмечает
оставшуюся неоднозначность, `paternalAlleleStatus` — `MATCH`, `AMBIGUOUS` или
`MUTATION`. `formulaAlleles` отдельно сохраняет кандидатов частотной формулы LR.
Для IDENT источник БД выбирается ролью `object`, `sourceType: "database"` и
`sourceId`; прежний вариант с `object1`/`object2` поддержан для совместимости.
Ручные изменения передаются через
`manualOverrides: {"TH01": "9,9.3"}` и не меняют профиль БД. Для полностью ручного
участника используются `sourceType: "manual"`, `displayName` и `manualOverrides`.
Поля `loci` от клиента не подменяют генотип источника БД. Для защиты от изменения
профиля между выбором и расчётом передавайте полученный `sourceDigest`.
Клиент не может подменить результат, версию формул, частот или владельца снимка.
PNG формируется в браузере из серверного отчёта целиком; кнопка копирования удалена.

Интеграционный тест использует только отдельную БД с именем
`dna_probability_test...` и переменную `PROBABILITY_TEST_DATABASE_URL`.
Без неё тест явно пропускается. Не указывайте рабочую БД.

Используйте актуальную версию Codex с поддержкой
[проектных агентов](https://learn.chatgpt.com/docs/agent-configuration/subagents).
После получения файлов откройте новую сессию Codex в папке репозитория, чтобы
загрузились определения и `AGENTS.md`. Агенты наследуют модель, права и MCP основной
сессии. Примеры запросов:

> Подключи агента dna_qa и проверь загрузку профилей на тестовом стенде.
>
> Проведи ревью параллельно агентами dna_security и dna_algorithms; дождись обоих
> и верни подтверждённые ошибки со ссылками на код.
>
> Поручи dna_devops проверить чистую установку в изолированной папке.

Подключения MCP хранятся в пользовательских настройках Codex, отдельно от Git:

```bash
codex mcp list
# Добавляйте только отсутствующие серверы:
codex mcp add playwright -- npx @playwright/mcp@latest --headless --isolated
codex mcp add sentry --url https://mcp.sentry.dev/mcp
```

[Playwright MCP](https://github.com/microsoft/playwright-mcp) позволяет агенту
открывать страницы и проверять UI. При первом использовании нужен установленный
совместимый браузер; используйте инструкции сервера, если он сообщает об отсутствии
браузера. Успешная проверка тестовой страницы не заменяет проверку приложения с
тестовыми пользователями и данными.

[Sentry MCP](https://mcp.sentry.dev/) требует аккаунт и OAuth-авторизацию.
Команда добавления может сразу предложить вход. Если вход отложен, после создания
аккаунта выполните `codex mcp login sentry`. После появления организации и проекта
подключение можно ограничить адресом
`https://mcp.sentry.dev/mcp/<organizationSlug>/<projectSlug>`.
Сам MCP не собирает ошибки приложения: для этого отдельно подключается Sentry SDK.
Не передавайте в Sentry генотипы, загруженные файлы, персональные данные и секреты.
Токены и настройки авторизации не должны попадать в репозиторий или `.env.example`.

Context7 используется для документации библиотек: сначала определяется library ID,
затем запрашивается документация нужной версии. Запросы не должны содержать данные
ДНК-профилей, секреты или закрытый код.

## Исправления безопасности (ноябрь 2026)

После обновления потребуется повторный вход: прежние JWT без идентификатора
сессии больше не принимаются. Refresh-токены хранятся в БД только как SHA-256,
ротируются при каждом `POST /api/auth/refresh` и отзываются при выходе, смене
пароля или деактивации пользователя. Клиент API должен сохранять **оба новых
токена** из ответа refresh. Повторное использование старого refresh отзывает
всё семейство сессии. WebSocket принимает только access-токен действующей
сессии и отключается при её отзыве или истечении срока.

Экспорты доступны создателю в исходном активном отделении в течение 24 часов.
Скачивание требует точного `exportId`; файлы, созданные до обновления без
метаданных владельца, необходимо сформировать заново. История и статистика
контаминации ограничены правами на оба профиля; анализ требует роли аналитика
или выше. Ручной `POST /health/persistence/verify` требует администратора и
ограничен двумя запросами в минуту. Публичный `GET /health` сохраняется.

Миграции **035** и **036** применяются штатными скриптами после резервной копии;
генотипы не переписываются. Для локальной разработки требуется Node.js 22.15 или
новее (контейнер использует Node.js 22 на Debian Bookworm). Версии зависимостей зафиксированы в lock-файле, используйте `npm ci`.

Проверки исправлений: `npm run check:ui`, `npm run check:imports`, `npm test`,
`npm run build`, `npm audit`. Дополнительный интеграционный тест
`tests/audit-remediation.integration.test.js` запускается только с отдельной
БД `dna_remediation_test...` через `REMEDIATION_TEST_DATABASE_URL`; он проверяет
экспорт, контаминацию, ротацию/отзыв сессий, WebSocket и служебные API на
синтетических данных. Рабочая БД для тестовых фикстур не используется.
