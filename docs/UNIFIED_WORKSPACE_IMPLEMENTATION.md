## Порядок выпуска

Сначала выборочная read-only выгрузка. Затем отдельная тестовая БД, схема,
черновики, workspace, полный поиск и публикация. Production-миграции и
переключение выполняются отдельным согласованным запуском после испытаний.
Старые данные, контейнеры БД, конфигурация и ключи не удаляются.

## Итоговая реализация

Персональные business tasks не создаются: `personal_workspaces` содержит один
постоянный UUID на организацию/владельца. Подтверждение импорта записывает только
выбранные строки в `dna_profiles.workspace_id`, не в общий реестр. Обязательны
полный номер, год и один из chs/ug/gr/staff; task, отделение и привоз не нужны.
Старые значения не удаляются. Регистрационный номер сотрудника, включая ведущие
нули, совпадает с полным номером объекта; ФИО требуется только staff.

Черновик хранится зашифрованно 24 часа, правки автоматически сохраняются с CAS.
В localStorage находятся только UUID черновика/ключ повторного commit, а не
генотипы. Ошибки снятой строки не блокируют выбранные; ошибочная включённая
строка откатывает весь пакет. Верхний выбор относится ко всему текущему фильтру.
Массовое изменение поддерживает незаполненные/все/выбранные строки, подтверждение
перезаписи и отмену. Сортировка не меняет UUID строк и индивидуальные значения.

Пустой профиль сохраняется, выгружается и снова читается как пустой; у него
`NO_GENOTYPE`, допуска публикации нет. Частично заполненный ниже порога получает
`INSUFFICIENT_DATA`. Пользовательское удаление — soft-delete; опубликованный
экземпляр и старые отчёты остаются.

Доказательство — `workspace_search_runs` + `workspace_search_profiles`,
зашифрованный результат, hash каждой анализируемой версии и три этапа.
Изменение генотипа/идентичности/состава workspace, настроек поиска или эталонов
инвалидирует допуск. Комментарий и ФИО не требуют пересчёта генотипов.
Деактивация общего массива тоже учитывается. Чужая рабочая копия не открывается
администратору через подстановку UUID. Подробная матрица ролей — в PERSONAL_WORKSPACE.

Публикация обычных — admin/sysadmin/head, staff — только admin/sysadmin.
История `workspace_publications` связывает рабочий UUID/ревизию, поиск и целевой
UUID. Конфликт обновления существующего эталона требует явного сопоставления
и повторной серверной проверки. Старый staff_id и опубликованный UUID при таком
обновлении сохраняются. Роль admin, `checked=true`, импортированный source UUID,
legacy approve/bulk-import и внутренний прямой INSERT не заменяют полный поиск.

Математика taskComparisonService, duplicate_v5, staff contamination и IDENT/TRIO
не переписана. Совпадение/контаминация показываются отдельно от технической
готовности. Сами совпадения не введены как новый автоматический запрет публикации.
Экспорт дубликатов использует прежний DuplicateExcelExportService.

NGS integration skip относится к недоступному внешнему образцу ASTR+, не к сбою
синтетических NGS/unit тестов. Стандартный npm test не запускает реальные
интеграции без явно заданных безопасных адресов; они выполнены отдельно.
В Docker build context проверено 342 JS / 1140 импортов: автономный
`probability-workbook-fixtures.js` намеренно исключён действующим .dockerignore.

При регрессии был найден конфликт deferred-trigger с CREATE INDEX в старой
миграции 029. Триггер ограничен действительно анализируемыми изменениями;
повторный полный genetic-import набор на окончательной схеме: 29/29.

Браузерный сценарий на отдельном Express/PG стенде использует реальные маршруты
и собранный frontend: фильтры выгрузки, XLSX → черновик без задачи/отдела,
смешанные годы/типы, staff, исключённая строка, пустой профиль, сохранение правок
после reload, удаление рабочей записи, блокировка непроверенной публикации,
полный поиск, экспорт дубликатов и явное сопоставление существующего staff.
Генетическая правка после поиска требует новой проверки. Скриншоты/журналы
синтетического стенда хранятся локально в ignored `runtime/validation`.

Тестовые PostgreSQL базы имеют `dna_*_test...` имена. Они находятся в том же
PostgreSQL-сервере, но не в production БД; INSERT фикстур в рабочую БД не выполнялся.
Docker web и Redis стенда отдельные, свободный порт 43194, отдельные каталоги
в runtime/validation. Рабочий web на 3001 не пересобирался и не заменялся.

## Ограничения и выпуск

- 037 применена только к тестовым БД. Production содержит прежнюю схему и образ;
  переключение, восстановление реальных данных и развёртывание нового режима
  требуют отдельного согласованного окна по LEGACY_EXPORT_AND_REIMPORT.
- Реальная production-схема не имеет канонического create_department_master_array
  trigger. Это проверено read-only; новый org-default array создаётся публикацией
  явно, не опираясь на несуществующий триггер.
- Нельзя автоматически угадать категории и годы исторических записей. Отсутствующие
  значения видны в выгрузке/черновике и требуют решения пользователя.
- Входные QC/конфликты просматриваются по строке; ручное исправление генотипа
  доступно через явный редактор JSON с сохранением исходного происхождения.
- В пользовательском списке нет жёсткого ограничения числа сохранённых объектов;
  одна групповая операция принимает до 10000 UUID, один multipart — до 100 файлов,
  10 МиБ на файл, 50 МиБ всего. Крупную миграционную выгрузку сервис делит на части.
- Excel ограничивает ячейку 32767 символами. Такой источник вызывает явную ошибку,
  а не скрытое усечение. Реальные файлы/историю сохраняйте отдельным backup.
- Технические регрессии не заменяют независимую научную валидацию моделей.
- В этом PR нет автоматического merge, production cutover или удаления старых данных.
