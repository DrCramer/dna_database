# Постоянный личный массив

Использована отдельная таблица `personal_workspaces`, а не скрытая бизнес-задача.
Уникальность `(organization_id, owner_id)` обеспечивается PostgreSQL.
Параллельные первые запросы возвращают один UUID. Рабочие профили остаются в
`dna_profiles`, получают `workspace_id`, категорию, комментарий, ФИО staff,
происхождение и ревизию. Новые записи не требуют department/task/import_number.

«Мои генотипы» открывает собственный массив. Он сохраняется после выхода,
перезапуска и обновления страницы. Переключение справочного отдела не меняет
его состав. В основной таблице есть год, тип, полный номер, ФИО сотрудника,
комментарий и динамический набор локусов. Колонки «Панель» нет; прежние UUID панелей
и их составы сохраняются, справочники доступны внутри организации без слияния имён.

Сортировка доступна по метаданным и локусам. Верхний чекбокс и кнопка выбора
относятся ко всему текущему фильтру, включая строки за пределами страницы.
Правки черновика автоматически сохраняются на сервере с проверкой ревизии.

Выбор профилей служит для полного поиска, удаления, XLSX и публикации.
«Удалить» выполняет soft-delete для аудита: профиль исчезает из действующего набора.
Опубликованный объект и прежние отчёты не удаляются. Повторная загрузка создаёт
новый UUID и не наследует допуск. Старые задачи доступны как архив, без новых
назначений, принятия, закрытия и публикации через approve.

## Права

| Роль | Свой массив | Загрузка при разрешённом праве | Поиск/экспорт своего | Публикация обычных | Публикация сотрудников | Выгрузка для переноса |
| --- | --- | --- | --- | --- | --- | --- |
| admin / system_administrator | читать/изменять | да | да | да | да | да |
| department_head | читать/изменять | да | да | да | нет | нет |
| user_analyst / совместимый analyst | читать/изменять | да | да | нет | нет | нет |
| viewer | чтение | нет | нет | нет | нет | нет |

Никто не получает право менять чужой личный массив подстановкой UUID, включая
администратора. Системный администратор в этих API также работает в организации
своей проверенной учётной записи. Общие опубликованные обычные профили читаются
внутри организации; сотрудники управляются отдельно административными ролями.

Для совместимости право загрузки вычисляется как OR прежних разрешений загрузки
в задачу/без задачи. Не требуется включать `can_upload_without_task` всем экспертам.
В новом меню пользователей показывается одно разрешение загрузки в личный массив;
старые поля API сохраняются. Права анализа/экспорта/изменения существующего массива
проверяются отдельно по роли, отключение загрузки само по себе их не выдаёт и не снимает.

## API

Все запросы требуют Bearer access token действующей сессии. Organization/owner
извлекаются сервером. Заголовок `X-Active-Department-Id` принимается для старых
клиентов и не меняет организацию либо область нового массива.

```http
GET    /api/workspace/config
GET    /api/workspace
GET    /api/workspace/profiles
PATCH  /api/workspace/profiles/:id
POST   /api/workspace/profiles/delete       {"ids":["UUID"]}
POST   /api/workspace/profiles/export       {"ids":["UUID"]}
PATCH  /api/workspace/search-settings       {"parameters":{"minMatches":15}}
POST   /api/workspace/full-search           {"ids":["UUID"],"parameters":{}}
GET    /api/workspace/searches/:id
POST   /api/workspace/searches/:id/duplicates-xlsx
POST   /api/workspace/publication-preview   {"ids":["UUID"]}
POST   /api/workspace/publish               {"ids":["только staff UUID"],"searchRunId":"UUID"}
```

Старые `/api/profiles`, `/search`, `/accessible`, `/:id`, `/master-objects/search`
и `/master-objects/:id` читают собственные рабочие и разрешённые опубликованные
обычные профили. DTO сохраняет полный `internal_number` и добавляет `objectNumber`,
`expertiseType`, `comment`. Чужие личные черновики не раскрываются DNAEXCEL.
Архивные маршруты записи профилей/сотрудников/задач не обходят новый pipeline.

IDENT/TRIO используют ту же математику, частоты и сохранённые снимки. Меняется
организационный выбор источников; прежние расчёты не пересчитываются.


## Два подтверждения перед мастер-массивом (миграция 038)

В «Моих генотипах» аналитик выполняет полный поиск, выбирает ЧС/УГ/ГР и открывает
«Действия → Отправить на подтверждение». Окно показывает состав, количество,
окончание анализа и явное сопоставление существующих мастер-записей. Все строки
должны иметь общий актуальный успешный запуск и CHECKED по трём этапам.
При разных запусках выполните полный поиск по выбору либо отправляйте группы отдельно.
Заявка хранит версии/хеши, выбранные целевые записи и зашифрованный снимок.
Пока статус «На подтверждении», мастер-записей нет.

Администратор назначает утверждающего в «Пользователи → Создать/Редактировать →
Загрузка ДНК-профилей → Окончательное подтверждение загрузки в мастер-массив».
Поле `users.can_approve_master` по умолчанию **false**, в том числе у администраторов.
Обычный пользователь с этим флажком видит кнопку «На подтверждении» в «Моих генотипах».
Очередь содержит чужие заявки только своей организации. После просмотра объектов,
совпадений, предупреждений и актуальных комментариев доступны «Подтвердить и загрузить»
и «Вернуть на доработку» с комментарием. Свою заявку решить нельзя.

«Мои заявки» и ссылка «Решение и история» в строке показывают состояния, участников,
оба подтверждения и возвращённые замечания после перезагрузки страницы. Решённая
заявка хранит зашифрованный снимок: последующие правки рабочей копии его не меняют.
После возврата исправьте данные, при необходимости повторите поиск и отправьте новую заявку.

| Действие | Аналитик | Администратор | Персональное право подтверждения |
| --- | --- | --- | --- |
| Отправка своих ЧС/УГ/ГР после полного поиска | Да | Да | Не требуется |
| Чтение своей истории | Да | Да | Не требуется |
| Чтение очереди и решение по чужой заявке своей организации | Только с флажком | Только с флажком | Требуется |
| Решение по своей заявке | Нет | Нет | Не разрешает |
| Выдача/отзыв флажка | Нет | Да, внутри организации | Не разрешает |
| Публикация эталонов сотрудников | Нет | Да, отдельной командой и после поиска | Не разрешает |

Время окончания анализа берётся из `workspace_search_runs.completed_at` **сохранённого**
`search_run_id` при `state='complete'`. Открытие завтра и более поздний поиск не меняют
эту дату. Время подачи и решения хранятся отдельно в `timestamptz`; окно показывает
их в часовом поясе **Europe/Moscow**. Отменённый/ошибочный запуск с completed_at допуском не является.

### API согласования

```http
POST /api/workspace/approval-preview  {"ids":["UUID"],"existingTargets":{}}
POST /api/workspace/approvals         {"ids":["UUID"],"searchRunId":"UUID","existingTargets":{},"idempotencyKey":"UUID"}
GET  /api/workspace/approvals
GET  /api/workspace/approval-history
GET  /api/workspace/approvals/:id
POST /api/workspace/approvals/:id/decision {"decision":"approve","reviewToken":"SHA256 из последнего GET","comment":""}
```

Для возврата используется `decision:"return"`. `reviewToken` защищает от изменения
данных уже открытого окна. При 409 перечитайте заявку; изменение генотипа, параметров,
состава или эталонных ревизий требует нового поиска и новой подачи. Прямой `/publish`
с ЧС/УГ/ГР отклоняется независимо от роли; он оставлен только для административной
публикации `staff`. Смешанный выбор разделите по назначению.

### Установка и обновление схемы

После установленной 037 примените `database/migrations/038_master_array_approval.sql`
с `ON_ERROR_STOP=1`, предварительно сделав резервную копию, затем запустите новый код.
Миграция не включает режим личных массивов и не назначает права автоматически.
Исторические публикации сохраняются с пустой ссылкой на новое согласование, без
выдуманного утверждающего. Скрипты install/update применяют 038 при наличии 037;
старый режим они самостоятельно не переключают. После ручной установки 037 выполните
038 до включения/запуска новой версии. В старом режиме скрипты добавляют только поле права.
