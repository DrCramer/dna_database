# Доступ DNAEXCEL к существующему API

## Причина ошибки 403

Поиск `/api/profiles/search` выполнялся по всей таблице без ограничения
отделением и ролью. Открытие `/api/profiles/:id` вызывало
`validate_department_isolation(userId, profileId)` без активного отделения.
Эта SQL-функция отсутствовала в `schema.sql`, `init.sql`, всех миграциях
репозитория и рабочей БД. Ошибка PostgreSQL перехватывалась и возвращалась
как `false`, поэтому техническая неисправность выглядела как отказ `403`.

До исправления проверка рабочего сайта с администратором, у которого
primary = ЧС, active = Генетические экспертизы, дала:
`search?q=258 → 200, 96 записей; GET найденного UUID → 403`.

## Общая проверка доступа

`src/services/profileAccessService.js` формирует одно условие для поиска,
списка `/accessible` и открытия UUID. `PermissionService.validateDataAccess`
для ДНК-профиля получает явный `activeDepartmentId` и использует этот сервис.
Зависимость от отсутствующей SQL-функции удалена.

1. JWT и действующая сессия проверяются существующим `authenticate`.
2. `X-Active-Department-Id` проверяется по доступным пользователю отделениям
   (`user_departments`; существующий fallback для старых пользователей без связей).
3. Организация выбранного отделения должна совпадать с организацией пользователя.
   Системный администратор может работать в явно доступных ему отделениях.
4. Принадлежность профиля определяется только `dna_profiles.department_id`
   и `organization_id`, а не основным отделением владельца.
5. Для всех трёх endpoints применяются одинаковые права:

| Роль | Чтение в активном доступном отделении |
| --- | --- |
| admin, system_administrator, department_head | Все профили выбранного отделения |
| user_analyst, legacy analyst, viewer | Собственные профили и профили мастер-массива отделения |

Администратор/руководитель может читать профили другого владельца в выбранном
отделении. Аналитик не получает нового доступа к чужим пользовательским профилям.
Смена primary владельца не меняет принадлежность загруженного профиля.

При отсутствии header сохраняется прежний выбор primary. Недоступный header
возвращает `403` и не подменяется primary. Профиль другого отделения возвращает
`403`, отсутствующий или деактивированный профиль — `404`. Поиск и `/accessible`
показывают только активные записи, которые можно открыть в том же контексте.

## Создание и изменение

Preview, обычная и пакетная загрузка уже получают проверенный активный контекст
через `getImportContext` / `ExcelService.resolveUserContext`. Контекст передаётся
в `create` / `batchInsert`, включая замену деактивированной записи новой.
Теперь модель требует явные отделение и организацию для обоих форматов импорта;
старый вспомогательный `bulkCreate` тоже передаёт эти поля. Дедупликация ЧС при
импорте ограничена выбранным отделением.

Изменение, удаление, деактивация и комментарии проверяют активный контекст.
Пользовательские операции записи сохраняют ограничение владельцем; viewer
не получает прав записи. Обновление профиля не позволяет изменить ownership
через поля тела запроса. Значения идентификаторов и структура STR не преобразуются.
Ответ GET сохраняет существующий формат (`sampleName`, `internalNumber`, `strData`).

## Схема и обновление существующей установки

Поле `dna_profiles.department_id`, организация, внешние ключи без каскадного
удаления профилей и индекс `idx_dna_profiles_department` добавлены ранее миграцией
**027**. Новая пустая установка получает их из `database/schema.sql`.
Новой миграции для этой исправленной версии не требуется.

Проверка рабочей БД перед обновлением:

```text
COUNT(*) = 6078
COUNT(department_id) = 6078
COUNT(organization_id) = 6078
Несовпадений организации профиля и отделения = 0
```

Дополнительный backfill не выполняется: неопределённых отделений нет.
Исторические записи уже заполнены миграцией 027. Известная принадлежность
не переписывается. Для иной установки с NULL сначала нужно изучить историю
загрузки/задач и восстановить только доказуемую принадлежность; runtime-проверка
не угадывает её по текущему primary владельца.

Обновление выполняется обычными командами из README после резервной копии.
Для старой установки, ещё не получившей 027/028, сначала выполнить инструкции
из `GENETIC_IMPORT.md` и `UPLOAD_PERMISSIONS.md`.

## Использование из DNAEXCEL

Сохраняется существующая последовательность:

```text
POST /api/auth/login
POST /api/auth/refresh
GET  /api/users/context
GET  /api/profiles/search?q=256
GET  /api/profiles/<UUID из поиска>
```

В `context`, `search` и GET профиля отправлять **один и тот же** header
`X-Active-Department-Id` и актуальный `Authorization: Bearer <accessToken>`.
Login/refresh сохраняют существующий контракт и не меняют primary при выборе active.
Специализированный API `/api/integrations/ikl/v1` в этой версии не добавляется.

## Диагностика

Каждый запрос получает `X-Request-Id`. Отказы возвращают
`code: PROFILE_ACCESS_DENIED`, технические ошибки проверки — HTTP **500**,
`code: PROFILE_ACCESS_CHECK_ERROR` и `requestId` в JSON.
В логах этих событий присутствуют userId, profileId, activeDepartmentId,
requestId, а при техническом сбое — реальная причина и код ошибки БД.
Генотип в эти диагностические события не записывается.

## Проверки

Добавлены 16 интеграционных сценариев в
`tests/profile-access.integration.test.js`, работающих с отдельной PostgreSQL:
primary == active; primary != active; ЧС ↔ Генетические экспертизы;
отказ для чужого владельца и разрешение руководителю/администратору;
viewer/legacy analyst; недоступные и чужие department UUID;
повреждённая межорганизационная связь; совпадение search/get/accessible;
фильтр типа и пагинация; отсутствующие/деактивированные записи;
refresh; запись/комментарии без смены ownership; явный контекст создания;
сбои БД проверки UUID, scope и middleware; содержимое диагностических логов.

Запуск: задать `PROFILE_ACCESS_TEST_DATABASE_URL` для **отдельной** БД с именем
`dna_profile_access_test` или `dna_profile_access_test_*`, предварительно
инициализированной `database/schema.sql`, затем:

```bash
node --test tests/profile-access.integration.test.js
```

Прежние тесты импорта выполняются с отдельной
`IMPORT_TEST_DATABASE_URL` (`dna_import_test_*`). `npm test` запускает оба набора,
если заданы обе переменные. Без переменных интеграционные наборы пропускаются;
unit tests продолжают выполняться. Тестовые профили синтетические.
