# Ночная сверка: установка и использование

Ночная сверка выполняет прежний полный поиск для активных личных массивов:
личный массив → мастер-массив организации → контаминации сотрудников.
Критерии, веса, пороги и выбранная версия алгоритма берутся из сохранённых
сервером настроек владельца. Генотипы не изменяются, результаты не публикуются
и не подтверждаются автоматически.

## Установка и обновление

`scripts/install.sh` и `scripts/update_server.sh` применяют новую миграцию
`040_night_search.sql` после резервной копии и до запуска нового приложения.
Миграция повторяется безопасно и не включает расписание. При ещё не переключённом
legacy-проекте создаётся только общий координатор CPU; таблицы ночных заданий
создаются после согласованного переключения через `scripts/workspace-cutover.sh`.
Повторно выполнять миграции 037–039 вместо штатного обновления не требуется.

Сохраняются `.env`, `config/encryption.key`, БД и все существующие локальные тома.
Новые постоянные данные находятся в PostgreSQL, дополнительный Docker volume,
Redis-плагин или отдельный пароль исполнителя не нужны.

## Настройка администратором

1. Откройте **Настройки → Ночная сверка**.
2. Задайте начало и окончание окна, часовой пояс IANA и дни недели.
   Дни относятся к **началу** окна. Например, понедельник 23:00–07:00 заканчивается
   утром вторника. Совпадающие начало и конец не допускаются.
3. Выберите поведение по окончании окна: пауза до следующего окна либо продолжение
   одним потоком. При отключении расписания задания по расписанию останавливаются
   независимо от этого выбора.
4. При необходимости раскройте «Ресурсы и пакеты». По умолчанию — максимум два
   потока и 16 объектов в пакете. Действует также общий `GENOTYPE_SEARCH_WORKERS`
   и ограничение CPU контейнера. Один объект против большого массива также
   распределяется по кандидатам.
5. Сохраните расписание. «Оценить объём» покажет актуальные массивы, необходимый
   пересчёт и пользователей без сохранённых настроек. Таким пользователям нужно
   сначала сохранить настройки/выполнить ручной поиск: браузерные значения
   localStorage недоступны ночному исполнителю.
6. «Пробный запуск сейчас» явно ставит нужные массивы в очередь вне расписания,
   даже при выключенной автоматике. Он имеет фоновый приоритет, не публикует данные
   и продолжает работу после закрытия браузера. Повтор команды с тем же ключом
   не создаёт копии заданий.
7. Для регулярной работы включите флажок расписания и сохраните. Вне окна новые
   задания по расписанию не начинают работу. Уже открытое окно обрабатывается при
   включении; пропущенные ночи по отдельности не воспроизводятся.

Настройка относится только к организации администратора. Управление расписанием
не даёт права `can_approve_master` и не открывает чужие личные генотипы.

## Очередь и результат

Обычный пользователь видит собственные задания, администратор может выбрать
очередь организации. Показываются этап, обработанные объекты, попытка, heartbeat,
паузы и ошибки. Список обновляется каждые 10 секунд и содержит последние 100 заданий.
«Пауза», «Продолжить», «Отменить» и «Повторить» проверяют организацию и владельца
на сервере. Пользователь не может возобновлением обойти окно расписания.

Готовый результат открывается владельцем кнопкой «Открыть результат» в том же
разделе анализа генотипов: таблицы, подсветка и Excel используют сохранённый снимок.
Администратор видит состояние чужого задания, но не получает ссылку на чужой личный
результат. Наличие совпадений не считается ошибкой выполнения.

Промежуточный/отменённый ночной запуск не заменяет предыдущую успешную проверку.
Актуальность всё равно зависит от текущих данных, параметров и версий эталонов.
Рассылка email и внешних уведомлений в этой версии не включена; история доступна
в приложении.

## Приоритет и восстановление

- Ночная работа разбита на пакеты; завершённые пакеты шифруются существующим ключом.
- Общий координатор PostgreSQL допускает один тяжёлый расчёт за раз между процессами
  приложения. Для него используется общий лимит workers, а не новый набор потоков
  на каждого пользователя.
- Ручной тяжёлый запрос прерывает фоновый пакет. В одном процессе это происходит
  сразу; между процессами запрос обнаруживается heartbeat примерно за секунду.
  Запись/чтение БД и сериализация также занимают время, это не гарантия фиксированной
  задержки всего HTTP-запроса.
- Прерванный пакет запускается повторно после ручной работы; готовые пакеты не
  теряются. Отмена CPU не выдаёт частичный CHECKED.
- При перезапуске аренда истекает через 40 секунд, после чего другой исполнитель
  может забрать задание. Старый токен не даёт записать результат.
- Изменение входов/настроек/эталонов меняет manifest и удаляет устаревшие контрольные
  точки. Финальная транзакция повторно проверяет ревизии, права и токен аренды.
- Завершённый результат, полные proof-записи и состояние задания записываются
  атомарно. Контрольные точки после успеха удаляются; полный результат сохраняется.
- Временные ошибки повторяются с задержкой, не более трёх ошибок на задание.
  Прерывание ручным поиском и закрытие окна не расходуют этот лимит.
- Контрольные точки отменённых/ошибочных заданий очищаются через 7 дней. Повтор
  такого задания пересчитает отсутствующие пакеты. Результаты и доказательства,
  связанные с публикациями, этим механизмом не удаляются.

Исполнитель встроен в web-процесс, но очередь долговечная и не зависит от HTTP.
Несколько web-экземпляров могут обслуживать её совместно через аренды и глобальный
координатор CPU. Если сервер выключен, вычислений нет; после запуска очередь
восстанавливается. Длительная транзакция БД на всю ночь не удерживается.

## Оптимизация в текущей версии

Полностью актуальные массивы пропускаются. Для устаревшего массива выполняется
полная сверка прежними алгоритмами с контрольными точками. При неизменном снимке
они повторно используются после паузы/перезапуска. Если снимок изменился, полный
пересчёт начинается заново.

Инкрементальный кэш отдельных направленных пар и журнал изменений эталонов пока
не включены. Это отдельный следующий этап из [проекта](NIGHT_SEARCH_DESIGN.md).
Нельзя переносить старый CHECKED в новую ревизию без доказательства полного покрытия.
Плотные массивы с большим числом совпадений требуют больше памяти и места под
результат; при необходимости уменьшайте пакет и число потоков. Ограничение heap
одного worker остаётся 256 МиБ; ошибка пакета не превращается в успешную проверку.

## API

Авторизация прежняя: `Authorization: Bearer <token>`, организация берётся из сессии.

| Метод и путь `/api/workspace` | Доступ |
|---|---|
| `GET /night-policy` | Расписание своей организации и `canManage` |
| `PUT /night-policy` | Только admin/system_administrator; обязательный `expectedRevision` |
| `POST /night-runs/preview` с `{}` | Оценка объёма, только администратор |
| `POST /night-runs` с `{ "idempotencyKey": "UUID" }` | Пробный фоновый запуск, только администратор |
| `GET /search-jobs?scope=own` | Собственная история |
| `GET /search-jobs?scope=organization` | Монитор своей организации, только администратор |
| `GET /search-jobs/:id/progress` | Владелец или администратор своей организации; без генотипов |
| `POST /search-jobs/:id/pause` с `{}` | Пауза |
| `POST /search-jobs/:id/resume` с `{}` | Возобновление с учётом окна |
| `POST /search-jobs/:id/cancel` с `{}` | Отмена |
| `POST /search-jobs/:id/retry` с `{}` | Повтор ошибочного/отменённого задания |

Пример тела сохранения политики:

```json
{
  "enabled": false,
  "timezone": "Europe/Moscow",
  "days": [1, 2, 3, 4, 5],
  "startTime": "23:00",
  "endTime": "07:00",
  "finishPolicy": "pause",
  "maxWorkers": 2,
  "chunkSize": 16,
  "expectedRevision": 0
}
```

При конфликте версии расписания — 409, чужой job — 404, недостаточном праве — 403.
Ночные результаты читаются и экспортируются через прежние защищённые маршруты
`/searches/:id`; ручной `/full-search/stream` сохраняет прежнее поведение.

## Проверки

`npm run check:ui`, `npm run check:imports`, `npm test`, `npm run build`.
Интеграция: `NIGHT_SEARCH_TEST_DATABASE_URL` должна указывать только на отдельную
БД `dna_night_search_test_...`; тест применяет 040 и использует синтетические данные.
Проверяются сохранение пакетов, повтор/аренда, расписание, DST, права, неизменность
генотипов, совпадение выдачи с ручным поиском, приоритет и отсутствие автопубликации.
