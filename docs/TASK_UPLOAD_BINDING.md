# Загрузка профилей в задачу и восстановление привязки

## Обновление действующего сервера

В папке проекта выполните:

```bash
./scripts/update_server.sh
```

Скрипт создаёт резервную копию БД, получает код с GitHub, пересобирает web и
проверяет состояние контейнера. Для этого исправления новой миграции не требуется.
После обновления обновите страницу браузера (Ctrl+F5).

## Работа в интерфейсе

1. Примите назначенную задачу: её статус должен стать **«В работе»**.
2. Откройте **«Загрузка профилей»** и проверьте **«Куда загрузить профили»**.
   Принятая задача выбирается автоматически. Если доступна одна задача «В работе»,
   страница импорта выбирает её даже после нового входа. При нескольких задачах
   выбор нужно сделать явно.
3. Выберите Excel-файл, проверьте предварительный просмотр и выполните загрузку.
4. Откройте анализ генотипов: загруженные профили находятся в выбранной задаче.

Загрузка без задачи требует одновременно права **«Загрузка без задачи»** в меню
пользователей и явного выбора **«Без задачи — отдельная загрузка»**.
Без этого сервер отклоняет запрос. Смена задачи или отделения сбрасывает выбранный
файл и предварительный просмотр. Назначение фиксируется до просмотра и сохраняется
при подтверждении загрузки.

## Контракт legacy API

Одинаковые требования действуют для multipart-запросов:

- `POST /api/profiles/upload/preview`
- `POST /api/profiles/upload`
- `POST /api/profiles/bulk-upload-with-comparison`

Передавайте файл в `file`, токен в `Authorization: Bearer …`, активное отделение
в `X-Active-Department-Id`.

| Назначение | Поля multipart |
| --- | --- |
| Доступная задача «В работе» | `taskId=<UUID>`; можно добавить `uploadTarget=task` |
| Разрешённая отдельная загрузка | `uploadTarget=without_task`, без `taskId` |

Также принимается `task_id`. Разные значения `taskId` и `task_id` отклоняются (400).
Одновременная передача задачи и `uploadTarget=without_task` отклоняется (400).
Без задачи и без явного режима отдельной загрузки запрос отклоняется (403 при
отсутствии права, 409 при наличии права). Параметры вроде `skipValidation`,
`validationOnly` и `can_upload_without_task` не обходят проверку прав.

Preview возвращает назначение в `preview.taskId`; upload и bulk — в `taskId`.
Созданные профили обычного upload содержат собственный `taskId`.
Перед INSERT сервер повторно проверяет актуальные права и статус задачи, блокирует
строки пользователя и задачи на время записи, проверяет все сохранённые привязки.
Если проверка не пройдена, вставка откатывается целиком.

## Уже загруженные профили: expert, задача 258

Команда выполняется **на сервере с проблемной БД**, в папке проекта после обновления.
Сначала получите отчёт; эта команда ничего не изменяет:

```bash
docker compose exec -T web node scripts/attach-profiles-to-task.js --task 258 --user expert
```

Отчёт содержит UUID задачи, количество уже привязанных профилей, число профилей
без задачи и список файлов/дат загрузок. Генотипы в отчёт не выводятся.
Если `orphanCount` равен 0, привязывать нечего: проверьте выбор задачи в интерфейсе.
При одинаковом названии нескольких доступных задач «В работе» укажите UUID в `--task`.
Отменённые и завершённые задачи исключены из поиска.

Если найдена ровно одна нужная загрузка, сделайте резервную копию и примените:

```bash
mkdir -p runtime/backups
umask 077
docker compose exec -T db pg_dump -U dna_user -d dna_analysis > "runtime/backups/before-task-binding-$(date -u +%Y%m%d_%H%M%S).sql" && \
docker compose exec -T web node scripts/attach-profiles-to-task.js --task 258 --user expert --apply
```

Если найдены несколько загрузок, уточните файл, а при необходимости и дату
**точно из отчёта**:

```bash
docker compose exec -T web node scripts/attach-profiles-to-task.js --task 258 --user expert --file 'profiles.xlsx' --uploaded-at '2026-10-06 12:00:00.123456' --apply
```

Команда привязывает только активные пользовательские профили **без задачи**,
принадлежащие указанному пользователю, организации и отделению задачи.
Проверяется доступ пользователя к задаче. Профили других пользователей, мастер-массив,
деактивированные записи и существующие привязки не изменяются. Изменяется только
`task_id`; контрольная сумма остальных полей проверяется до фиксации транзакции.
Повторный запуск для той же загрузки ничего не изменяет.

Перед изменением сохраняется приватный JSON со списком ID и предыдущей привязкой
в `/app/backups/profile-task-repair-….json` (на хосте `runtime/backups`, права 0600).
Он нужен для адресной отмены привязки; полная SQL-копия позволяет восстановить БД.
Операция записывается в историю как `PROFILE_TASK_BINDING_REPAIR`, источник `server-cli`.
При любой ошибке проверки изменения БД откатываются.

После применения обновите страницу, выберите задачу 258 и откройте анализ генотипов.
