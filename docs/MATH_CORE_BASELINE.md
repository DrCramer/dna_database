# Расчётное ядро: базовые проверки перед рефакторингом

Дата: 13 октября 2026 года. Фаза 1 согласованного аудита.
Исходная версия расчётного кода: `1e277f94f6f3a0c898a004afb5aaba908f65c395`.

## Границы проверки

В этой фазе добавлены тесты; реализации расчётов, валидация аллелей,
импорт панелей, схемы БД и алгоритмы поиска не изменялись.
Тесты сохраняют воспроизводимость текущего поведения. Они не являются
валидацией математической модели для экспертного заключения.

Все фикстуры синтетические. Производственные ДНК-профили, учётные данные
и частотные базы не используются. `BayesianEngine` загружается с подменой
модулей БД, Redis и пула соединений до исполнения его зависимостей;
это исключает сетевые запросы и создание таймера настоящего пула.
Worker запускается как настоящий `worker_threads.Worker` с синтетическими данными.

Эталонные числа задаются отдельно от вызовов проверяемого кода. Например,
при частотах `p=0.2`, `q=0.3` базовые вероятности составляют `0.04` и `0.12`.
При `theta=0.1`, `F=0` существующая расширенная реализация даёт `0.0784`
и `0.2072`. Для двух синтетических локусов зафиксировано произведение
`0.04384352`. Проверка чисел использует абсолютный допуск `1e-12`.

Drop-out/drop-in в этих тестах означает нынешние множители параметров
`dropOutProbability` / `falseAlleleProbability` и отношения включения аллелей
в V5. Это не подтверждает наличие полноценной вероятностной модели смеси.

## Воспроизводимые дефекты

Ниже перечислены **выполняемые TODO-тесты**: они проверяют ожидаемый контракт
и сейчас воспроизводят ошибку. Node.js не включает TODO в число обычных
падений и возвращает успешный код завершения. Поэтому зелёный `npm test`
нельзя трактовать как отсутствие этих дефектов. После согласованного
исправления соответствующую пометку `todo` необходимо удалить.

| ID | Дефект | Место воспроизведения |
| --- | --- | --- |
| MATH-01 | `calculateProfileLR()` возвращает `locusLRs` как объект, `generateLRReport()` ожидает итерируемый `Map` и падает | `tests/lr-calculator.test.js` |
| MATH-02 | `countSTRLoci()` не читает массивы аллелей из `str_data`; валидный профиль получает «недостаточно STR» | `tests/degradation-analyzer.test.js` |
| MATH-03 | `countSTRLoci()` использует `Object.entries()` для `Map`, теряя все локусы | `tests/degradation-analyzer.test.js` |
| MATH-04 | `ContaminationDetector` учитывает `?` и `*` при определении многоаллельности | `tests/contamination-detection.test.js` |
| MATH-05 | Worker принимает одинаковые пары `12,?` за совпавший локус | `tests/genotype-comparison-worker.test.js` |
| MATH-06 | Хэш набора профилей для БД не различает изменения после первых пяти ID | `tests/bayesian-engine.test.js` |

Дополнительно требуют согласования семантики:

- `calculateLocusLR()` возвращает рассчитанную вероятность генотипа,
  не вычисляя отношение двух гипотез. Это явно обозначено в названии
  соответствующего baseline-теста; математическая модель не заменялась.
- При отсутствии признаков байесовская оценка контаминации равна
  `0.07585818002124355` вследствие текущей сигмоиды.
- V5 определяет редкость по микроаллелям, а правило трёх критических
  локусов может сработать и для целочисленных аллелей без частотных данных.
- В `BayesianEngine.findDuplicates()` вычисленный хэш пространства
  поиска не передаётся в ключ кэша БД. Исправление требует проверки
  совместимости кэша и его изоляции в отдельном шаге.

## Результаты

До добавления тестов: **119 сценариев, 114 прошли, 5 пропущены, 0 падений**.
Новые тесты ядра: **64 сценария, 58 прошли, 6 TODO, 0 обычных падений**.
Полный набор после добавления: **183 сценария, 172 прошли, 5 пропущены,
6 TODO, 0 обычных падений**.

Пять существующих интеграционных тестов требуют отдельных тестовых БД;
в стандартном `npm test` они пропускаются. Unit-проверки ядра ничего не
записывают в рабочую БД.

Команды проверки:

```bash
node --test tests/lr-calculator.test.js tests/bayesian-engine.test.js \
  tests/contamination-detection.test.js tests/degradation-analyzer.test.js \
  tests/genotype-comparison-worker.test.js
npm test
npm run check:ui
npm run build
```

Production-сборка и запуск backend проверяются отдельно в Docker
с временными PostgreSQL/Redis, синтетическими секретами и свободным
локальным портом. Рабочий контейнер и его БД для проверки не перезапускаются.

Результаты проверки образа `dna_database-web:math-phase1-check`:

- Node.js 20: полный набор — 172 прошедших сценария, 5 пропущенных, 6 TODO.
- `npm run check:ui`: успешно (40 таблиц стилей, 2674 селектора).
- `npm run build`: успешно; два предупреждения Webpack о размере bundle,
  ошибок сборки нет.
- Backend стартует в `NODE_ENV=production`, байесовский модуль инициализируется.
- `/health`, `/health/ready` и `/`: HTTP 200. Итоговые статусы —
  `healthy` и `ready`.
- Схема и начальные локусы созданы из `database/schema.sql` и
  `database/seed_loci.sql`, администратор — штатным `scripts/bootstrap-admin.js`.
  До заполнения пустой тестовой БД persistence давал предупреждение об
  отсутствии пользователей/локусов; после bootstrap все проверки healthy.
- Тестовые контейнеры используют отдельную сеть и временные данные;
  конфигурация и тома production не задействованы.
