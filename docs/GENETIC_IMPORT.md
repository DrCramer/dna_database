## Формат и определение отделения

Источник формата — активное отделение, проверенное `authenticate` по
`X-Active-Department-Id`. Preview и upload строят одинаковый контекст через
`getImportContext()` и `ExcelService.resolveUserContext()`. Доступ повторно
проверяется по `User.getAccessibleDepartments()`; основное отделение не заменяет
переданное активное. Название и организация берутся из справочника departments.
UUID отделений не зашиты в код.

`resolveProfileImportFormat()` выбирает `genetic` для «Генетические экспертизы»,
`emergency` для «ЧС». Для остальных отделений сохранена историческая проверка.
Параметр формата из тела HTTP-запроса не используется.

Для genetic:

```text
Объект | TH01 | D5S818 | D21S11
A-1    | 7,9  | 11,12  | 29,30
```

«Объект» должен находиться в A1. После него нужны минимум три разных
поддерживаемых локуса в любом порядке. Пример не задаёт обязательный набор.
Год и служебные столбцы не нужны; неизвестные и повторные заголовки — ошибки.
Полностью пустые строки игнорируются, номера ошибок соответствуют строкам Excel.
Отдельные локусы могут быть пустыми, весь профиль без данных отклоняется.

## Канонические имена и аллели

`LociTypeDetector.getCanonicalLocusName()` возвращает каноническое имя из
каталога поддерживаемых локусов, учитывает регистр, пробелы и варианты
`PentaD`/`Penta D`.
Общая проверка `validateGeneticHeaders()` создаёт карту `{ index, locus }`.
`extractGeneticProfileFromRow()` читает значение той же колонки и сохраняет
его под каноническим именем в `str_data`. Порядок колонок нигде не становится
идентификатором локуса.

Используется существующий `parseAlleleValue()` и валидаторы SNP/STR/AMEL.
Гомозиготы и разделители сохранены. Гаплоидная обработка Y-маркеров теперь
определяется типом `Y_CHROMOSOME`, включая DYS392 и SRY. Исторический `Yindel`
сохраняет прежнюю обработку. Зарегистрированные `rs199815934`, `Rs771783753`
и `rs759551978` имеют отдельный тип `Y_INDEL`: принимаются строковые значения
`1` и `2`, одиночное значение не дублируется, а несколько значений сохраняются
с предупреждением о возможной смеси или аномалии. Типы `rs`-локусов берутся из
реестра маркеров, а не выводятся по одному префиксу. Алгоритмы сравнения обращаются
к локусам по имени; тест подтверждает независимость от перестановки колонок.

## Хранение и дубликаты

- `sample_name` — значение «Объект», с удалением крайних и повторных пробелов.
- `internal_number` — то же значение для совместимости существующих экранов.
  Случайные номера не генерируются; латинские буквы объекта не заменяются кириллицей.
- `year = NULL`, `import_number = NULL`. Год не извлекается и не подставляется.
- `import_format`, `department_id`, `organization_id` сохраняются в профиле.
  Notes дополнительно содержат источник, номер строки и контекст импорта.

Genetic-дубликаты определяются по нормализованному имени объекта в scope:
**организация + активное отделение + владелец**, с сохранением существующей
изоляции личных профилей. Регистр и крайние пробелы не создают новый объект.
Одинаковые генотипы разных объектов разрешены. Preview различает `create`,
`conflict` и `replace`; неактивная запись не препятствует созданию новой активной
версии. Проверка действует даже при `allowDuplicates=true` и выключенной
опциональной дедупликации. Частичный уникальный индекс защищает от одновременной
загрузки одного объекта. Дубликаты внутри файла обнаруживаются до записи в БД,
с номерами первой и повторной строк.

Год обязателен для новых профилей ЧС и проверяется моделью и ограничением БД.
Миграция не переписывает годы исторических профилей. Их принадлежность отделению
заполняется из данных владельца; исторические записи сохраняют legacy-формат.

Тот же принцип применён к `master_array_profiles`: перенос после утверждения
задачи сохраняет `year = NULL` и `metadata.importFormat = genetic`. Добавление
в мастер-массив проверяет разрешённые пользователю отделения и дубликат объекта.
Для записей ЧС год остаётся обязательным. При опциональном сравнении во время
загрузки используется мастер-массив активного отделения, а не основного.

## UI и совместимость ЧС

Справка загрузки зависит от `activeDepartment` из AuthContext. Для genetic
показывается новый пример и пояснение о произвольном порядке локусов. В ошибках,
результатах и подтверждении замены не выводятся пустые год/номер; доступны
объект, число локусов и статус. Смена отделения очищает прежний файл и preview.
Запросы одной операции сохраняют выбранное при старте отделение.
В деталях ошибок используется исходный номер строки Excel, включая пропущенные
пустые строки.

ЧС использует прежний parser, mapping присвоенного номера/привоза/года/названия
образца, проверки и пример. В FileValidationService согласованы два уже
поддерживаемых parser названия из старого UI-примера: «Наименование образца»
и «присвоенный в в/ч …». Обязательные значения и формат данных ЧС сохранены.

Исправлены связанные проблемы: модель не включала `year` в JSON, метод
`countByUserId()` отсутствовал, один SQL-запрос списка содержал пропущенные `$`
перед параметрами. Выборки анализатора теперь используют отделение самого
профиля с fallback на владельца, чтобы переключившийся пользователь видел
загруженные профили. Позиционной зависимости локусов в алгоритмах не найдено.

## Обновление существующей установки

Новая установка использует обновлённый `database/schema.sql`. Для существующей
БД **перед запуском нового web-образа** примените миграцию 027:

```bash
cd /путь/к/dna_database
set -e
umask 077
mkdir -p runtime/backups
docker compose exec -T db pg_dump -U dna_user -d dna_analysis \
  > "runtime/backups/before_genetic_import_$(date -u +%Y%m%d_%H%M%S).sql"
docker compose build web
docker compose stop web
docker compose exec -T db psql -U dna_user -d dna_analysis -v ON_ERROR_STOP=1 \
  < database/migrations/027_genetic_profile_import.sql
docker compose up -d --no-deps web
docker compose ps
```

Если миграция завершилась ошибкой, не запускайте новый образ до устранения
причины. Миграция выполняется в транзакции и допускает повторный запуск.
Скрипт `update_server.sh` останавливает автоматическое обновление при изменении
схемы: выполните указанные выше шаги после получения новой версии исходников.
После перезапуска web потребуется повторный вход из-за хранения сессий в памяти.

## Проверки

Команды выполняются **в корне проекта** — отдельного frontend/package.json нет:

```bash
npm ci --include=dev
npm test
npm run check:ui
npm run build
```

По умолчанию запускаются unit-тесты. Интеграционные тесты включаются при заданном
`IMPORT_TEST_DATABASE_URL`: только отдельная БД с именем `dna_import_test` или
начинающимся с `dna_import_test_`, с установленной схемой. Рабочую БД для них
не используйте. Например:

```bash
IMPORT_TEST_DATABASE_URL='postgresql://user:password@127.0.0.1:5433/dna_import_test' npm test
```

Проверены все 31 локус из задания и несколько перестановок; регистр/Penta,
пустые строки и поля, неизвестные/повторные заголовки, гаплоидные маркеры/SNP,
дубликаты объектов, отсутствие года, старый ЧС, смена активного отделения,
отказ доступа к чужому отделению, одинаковый mapping preview/upload,
create/conflict/replace, SQL-ограничения и чтение новых профилей анализатором.
Старая схема обновлена миграцией в отдельной БД; новая reference-схема также
развёрнута и проверена. Исторический `init.sql` отдельно развёрнут с тестовым
пользователем; устранена коллизия имени отделения в его view после добавления
контекста профиля. Тестовые данные — синтетические.

Итог: **30 проверок прошли**, включая перенос в мастер-массив. `npm ci`,
`check:ui` и production build выполнены; webpack выдал только два предупреждения
о размере bundle/entrypoint (~1.50 MiB). Docker также выполняет unit-тесты при сборке.

После обновления рабочей установки проверены HTTP health, preview genetic-файла
с переставленными заголовками и переключение ЧС ↔ Генетические экспертизы в браузере.
Preview вернул `year = NULL`, четыре локуса и действие `create`; синтетические
профили в рабочую БД не записывались. При смене отделения файл очищается, пример
меняется, горизонтального переполнения страницы при ширине 768 px нет.
Отдельно проверено отображение результата и ошибки на синтетическом ответе API
в браузере: объект, четыре локуса, статус загрузки и исходная строка 5;
пустой год и служебный номер не выводятся. Запись в рабочую БД была перехвачена.
