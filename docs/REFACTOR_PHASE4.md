# Рефакторинг: Фаза 4 — доступ, шифрование и ошибки API

Дата проверки: 13 октября 2026 г. Фаза подтверждена пользователем после плана Фазы 3.

## Доступ

`src/services/security/AccessPolicyService.js` содержит серверные решения о
правах, областях профилей, задачах, отделениях, загрузке и истории. SQL-проверки
перенесены из middleware. Аутентификация JWT, транспортные проверки наличия
контекста и аудит остаются в middleware; выбор разрешений делегируется сервису.

Совместимые `permissionService`, `profileAccessService`, `profileUploadPolicy`
сохраняют прежние точки входа. Express-фабрики вынесены в
`src/middleware/permissionChecks.js`; дублирующаяся фабрика проверки отделения
в auth использует её. Старые call sites менять не требуется.

`src/utils/accessPolicyRules.js` — чистые общие правила для browser/backend:
флаги загрузки, причины запрета, списки ролей для операций и истории.
`profileUploadPermissions.js` сохраняет совместимые экспорты. Браузерные
правила не импортируют БД или серверные middleware.

До переноса зафиксирована матрица сценариев: шесть ролей, чтение/запись,
active/primary department, организация, история, явный выбор «Без задачи»,
флаги прав, UUID задачи, статус, доступ к назначению и блокировка `FOR SHARE`.
После переноса те же проверки проходят.

Сохранены различия исторических контекстов: alias `analyst` в авторизации
маршрутов, отдельные разрешения истории/статистики, generic resource permissions
и операции загрузки. `admin` не превращён в глобальный `system_administrator`.
У старых middleware есть явно обозначенные legacy-методы внутри единого сервиса;
они не подменяют canonical область поиска профилей в активном отделении.
Этот перенос не переопределяет матрицу прав и не подключает старые middleware
к новым маршрутам.

Исправлена реальная ошибка старого helper проверки группы:
`expert_group_members.expert_group_id` заменён на существующий `group_id`.
На настоящей схеме проверены активное членство, права группы на задачу,
отсутствие членства и отказ после деактивации участника.

## Шифрование

Общие AES-операции выделены в `security/cryptoPrimitives.js`:
CBC (IV 16 байт) и GCM (IV 12 байт). `SecurityConfig` и
`databaseEncryptionService` используют одни функции encrypt/decrypt.
Предметный `encryptionService` уже делегировал обоим адаптерам и продолжает
использовать их без смены полей объектов или конфигурации email.

Форматы сохранены:

- `SecurityConfig`: `iv_hex:ciphertext_hex`;
- DB-адаптер: JSON `{ algorithm, iv, data, authTag, version, timestamp }`,
  байты в base64, `version=1`, `authTag=null` для CBC.

Ключи, парольное хэширование, политики ротации и строки БД не переписывались.
Прежний CBC не заменяется GCM автоматически: такая миграция требует отдельного
плана совместимости и восстановления.

В `tests/fixtures/encryption-baseline.json` сохранены шифротексты, созданные
старым кодом до переноса. Ключ `Buffer.alloc(32,17)` и значения синтетические.
Проверены чтение старых строк, независимое native AES-декодирование новых
записей, Unicode, пустые значения, свежий IV, отклонение подмены GCM,
пользовательский адаптер с обоими значениями ENCRYPT_USER_EMAIL.
Существующий тест проверяет сохранность ключа и расшифровку в новом процессе.

## Публичные ошибки

`src/utils/apiErrors.js` задаёт общий контракт:
`success=false`, `message`, `code`, `status`, `requestId`, `timestamp`, `error`.
Тип старого поля `error` сохраняется — строка или объект; клиенты могут
пользоваться верхними полями независимо от старого варианта ответа.

`apiErrorResponses` в `src/middleware/errorHandler.js` подключён для `/api`
до body parser. Он нормализует как явные ответы routes, так и исключения,
текстовые rate-limit ответы и sendStatus. HTTP-коды сохраняются; успешный JSON,
XLSX и health-эндпоинты не меняются. Неизвестный `/api` возвращает JSON 404,
а не HTML SPA. После отправки заголовков исключение передаётся Express для
корректного завершения потока.

При 5xx в production произвольный payload и внутренний текст исключаются из
ответа; доступны общий текст, безопасный код и requestId для поиска в логах.
Стеки, SQL, пути, ключи и контекст профилей не выдаются в этих ответах.
Диагностика остаётся в серверном logger с тем же requestId.

В Bayesian ErrorHandler публичные `toJSON`/`toApiResponse` используют тот же
сериализатор. `toDiagnosticJSON` сохраняет прежний внутренний отчёт для
журнала и статистики; проверки образцов, аллелей, классификация и стратегии
восстановления сохранены. Формулы расчётного ядра не менялись.

## Проверки

После baseline и каждого самостоятельного шага выполнялись тесты, UI, импорты
и production webpack build. Финальные результаты:

- обычный прогон: 206 тестов, 195 pass, 5 skip, 6 TODO, 0 fail;
- расширенный прогон на пяти новых PostgreSQL БД:
  262 теста, 254 pass, 1 skip, 7 TODO, 0 fail;
- импорты: 263 JS-файла, 821 относительная ссылка, неразрешённых нет;
- UI: 40 stylesheets, 2674 selectors, 72 animations;
- Docker/Node 20: все build gates прошли; webpack имеет две прежние
  рекомендации о размере bundle;
- LRCalculator, BayesianEngine, DegradationAnalyzer, ContaminationDetector,
  contaminationAlgorithm и genotypeComparisonWorker не имеют изменений.

Production smoke выполнен с отдельными PostgreSQL/Redis, синтетическими
данными и отдельным ключом:

- bootstrap admin, login, HTTP сайта 200, полное состояние health `healthy`;
- 104 профиля: одинаковые single-threaded/multi-threaded результаты,
  snapshot 5356 пар, чужое отделение исключено;
- настоящий XLSX-экспорт, листы «Профили»/«Сравнения», отказ 403 при экспорте
  snapshot из другого отделения;
- чтение шести шифротекстов старых форматов, ключ не изменён;
- реальный HTTP-контракт 400/401/403/404/500, requestId совпадает с заголовком;
- временный сбой таблицы только в отдельной тестовой БД: ответ 500 не выдаёт
  внутренние детали; таблица восстановлена, health повторно `healthy`;
- Playwright: login, bayesian, смена вкладок и excel-converter без pageerror
  и console.error.

Один skip — необязательный частный NGS-образец. Шесть прежних математических
TODO и DB-01 остаются открытыми; они не включены в число pass.
