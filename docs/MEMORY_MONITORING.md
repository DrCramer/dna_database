# Контроль памяти сервера

На общем сервере с 8 ГБ RAM много контейнеров. Без ограничений сумма их пиков,
сборка, Chromium и вычисления могут заполнить RAM и swap. Замер одного приложения
не объясняет потребление всей машины. Мониторинг фиксирует свободную память,
swap, uptime и десять крупнейших процессов по RSS + swap; аргументы команд,
секреты, ФИО и генотипы не записываются.

## Постоянные замеры

Для установки на сервере с Python 3 и пользовательским systemd:

```bash
./scripts/install-memory-watch.sh
systemctl --user status dna-memory-watch.timer
python3 scripts/memory-watch.py --once
```

Таймер выполняется каждую минуту, сам ограничен 64 МиБ и 10% CPU.
Для запуска без открытого сеанса нужен `Linger=yes`:

```bash
loginctl show-user "$USER" -p Linger
# При необходимости администратор сервера включает:
loginctl enable-linger "$USER"
```

Последний замер: `runtime/monitoring/memory.json`.
История: `runtime/monitoring/memory.jsonl`; при достижении 5 МиБ сохраняется одна
предыдущая копия. Файлы имеют права 0600, папка 0700.
Статус warning появляется при свободной памяти менее max(768 МиБ, 10% RAM),
critical — менее max(256 МиБ, 4% RAM). Почти заполненный swap также учитывается,
если остаётся менее 20% свободной RAM. Сам по себе занятый swap после нагрузки
не доказывает продолжающуюся нехватку памяти.

Монитор не останавливает посторонние сервисы и не рассылает данные наружу.
Это постоянный локальный сбор замеров; ручное наблюдение агента после завершения
диалога не продолжается. Просмотр:

```bash
cat runtime/monitoring/memory.json
journalctl --user -u dna-memory-watch.service -n 10
```

## Ограничения DNA Database

В `docker-compose.yml` заданы следующие значения по умолчанию:

| Сервис | RAM | RAM + swap | Дополнительно |
|---|---:|---:|---|
| web | 2048 МиБ | 2304 МиБ | heap главного Node-процесса 768 МиБ |
| PostgreSQL | 1024 МиБ | 1280 МиБ | существующие данные и volume сохраняются |
| Redis | 256 МиБ | 256 МиБ | maxmemory 128 МиБ, noeviction |

Настройки переопределяются переменными из `.env.example`. `mem_reservation` —
мягкая граница, а не предварительное выделение памяти. Лимит Node heap не включает
весь RSS: buffers, код и отдельные worker heaps учитываются лимитом контейнера.
Достижение жёсткого лимита может завершить процесс контейнера; это предохранитель,
а не гарантия, что любая нагрузка поместится. При Redis maxmemory новые записи
могут быть отклонены; существующие данные не вытесняются автоматически.

Расчёт числа потоков учитывает и CPU, и текущий запас RAM хоста/контейнера.
Ночная сверка не начинает работу при свободной RAM хоста менее 1 ГиБ или запасе
контейнера менее 768 МиБ; текущая работа приостанавливается с сохранением
завершённых пакетов. Затем очередь автоматически продолжает работу. Приоритет
ручного поиска сохраняется. При критически малом запасе памяти ручной тяжёлый
поиск возвращает понятную ошибку 503 вместо запуска новых workers.

`/health` показывает RSS, доступную память хоста и запас контейнера. При низком
запасе статус degraded; это не вызывает постоянных перезапусков приложения.

## Сборка и обновление

`install.sh` и `update_server.sh` перед сборкой требуют не менее 1536 МиБ
MemAvailable. Проверка выполняется до остановки контейнеров. В Docker build
heap Node ограничен 768 МиБ. Параллельные сборки и нагрузочные тесты на общем
сервере следует запускать последовательно. Порог перед стартом не резервирует
RAM и не исключает одновременную нагрузку других сервисов.

Лимиты этого проекта не ограничивают другие контейнеры сервера. Если при обычной
работе постоянно мало доступной RAM и растёт swap, требуется распределить лимиты
остальных сервисов либо увеличить память/перенести часть нагрузки.
