# NGS ASTR+ в конвертере Excel

## Порядок работы

В отделении «Генетические экспертизы» откройте **Конвертер Excel**, выберите NGS-файлы и нажмите **Проверить и объединить**. Их можно обрабатывать вместе со старыми таблицами.

1. Для каждого NGS-файла укажите полный номер объекта и нажмите **Подтвердить номер**. Из `r2.251-3_20260714.ASTR+.xlsx` предлагается `251-3`, но предложение само по себе не разрешает экспорт. Неузнаваемое имя оставляет поле пустым.
2. Введите год и нажмите **Применить год**. Год входит в идентификатор вместе с полным номером объекта. Номер экспертизы извлекается из полного номера существующим импортом.
3. При необходимости назначьте доступную панель. Название файла не создаёт панель и не назначает её автоматически.
4. Сверьте отчёт о маркерах: поддерживаемые имена, aliases, неизвестные и неоднозначные. Неизвестный маркер блокирует экспорт: его необходимо сопоставить с проверенным именем каталога либо явно исключить. Исключённые данные остаются в аудите.
5. Откройте нужный локус в NGS-предпросмотре. Таблица деталей показывает все записи Result/Detail, QC, Coverage, Proportion, Flanking SNP. Структура и последовательности доступны в раскрываемых исходных полях.
6. Для спорных генотипов подтвердите исходный набор, примите предложенный вариант, введите собственные аллели, отметьте неопределённый результат либо исключите результат локуса. Можно записать причину. Решение получает дату и сохраняется вместе с исходными данными.
7. После разрешения ошибок и конфликтов скачайте XLSX или нажмите **Передать в загрузку профилей**. Передача также требует указания года. На странице загрузки применяется обычный выбор задачи, preview и проверка прав.

## Распознавание и транспозиция

`geneticSourceDetector.detectSourceFormat()` проверяет содержимое листов `Result` и `Detail`, а не имя файла. Регистр, окружающие пробелы и порядок колонок не важны. Заголовки ищутся в первых 30 строках.

- Result: `#Type`, `Locus`, `Genotype`, `QC Flag`, `Total Depth of Coverage`.
- Detail: `Locus`, `Allele`, `QC Flag`, `Coverage`; дополнительные поля, включая тип, сохраняются по названиям.

Отсутствующий Detail даёт ограниченную уверенность и требует подтверждения непустых генотипов. Отсутствующий Result или повреждённые обязательные заголовки блокируют обработку. При неоднозначности можно явно выбрать формат, листы и строки заголовков.

`ngsAstrExcelParser.js` создаёт промежуточную модель и связывает записи по каноническому локусу и типу маркера. Несогласованный тип не становится подтверждающим доказательством. Записи только из Detail тоже показываются: из них генотип автоматически не создаётся. Служебные числа покрытия и проценты не используются как аллели.

Один файл преобразуется в одну строку генотипов. Эта строка проходит существующие нормализацию, объединение объектов, разрешение конфликтов, экспорт и импорт. Одинаковый номер и год в двух файлах не перезаписываются молча. Старый парсер продолжает обрабатывать обычные горизонтальные таблицы.

## QC и решения

| Ситуация | Поведение |
| --- | --- |
| Result и Detail согласованы, все флаги Pass, корректное ненулевое покрытие | Автоматически допустимый генотип после общей нормализации |
| Stutter, Imbalance, Flanking SNP | Требуется проверка; исходные флаги сохраняются |
| Low Coverage, Failed при непустом генотипе | Требуется явное решение |
| Неизвестный или пустой QC | Требуется проверка, не считается Pass |
| Нет генотипа, нулевое покрытие, Failed/Low Coverage | Пустая ячейка, статус MISSING и сохранённая причина |
| Result и Detail расходятся либо есть дополнительные Pass | Требуется решение |
| Более двух аллелей | Сохраняются все; экспорт заблокирован до решения |
| Одна аутосомная аллель | Существующий SINGLE_DIPLOID: гомозигота либо неизвестная вторая аллель |
| Одинаковая длиновая аллель с разными последовательностями | Требуется проверка; все варианты остаются в аудите |

Числовые пороги качества не изобретаются. При нескольких аллелях предложение двух основных значений появляется только если в Detail есть ровно два различных сигнала Pass с ненулевым покрытием и оба указаны в Result. Это предложение никогда не применяется автоматически и не заменяет проверку экспертом.

Нормализацию выполняет общий `normalizeAlleleValue()`. Микроварианты сохраняют десятичную точку. Одиночное значение не становится гомозиготой автоматически: текущая модель представляет неизвестную вторую аллель как `?`. Для NGS массовые правила старых файлов не снимают индивидуальную QC-проверку.

При подтверждении смеси в аудите сохраняется `multiAllelicConfirmed`. В предпросмотре многокомпонентные результаты явно отмечены; принятые массивы аллелей сохраняются при стандартном импорте и не сокращаются до двух значений. Алгоритмы сравнения, дубликатов и контаминации в рамках этой доработки не меняются.

`SRY` с типом SEXUAL и значением `SRY` поддерживается как отдельный гаплоидный маркер: сигнал сохраняется один раз, QC проверяется по общим правилам.

AMELX/AMELY объединяются только в один импортируемый AMEL. Проверяются исходные сигналы обоих маркеров. При наличии только X или только Y не добавляется второй сигнал и не выводится пол. Неполный AMEL требует подтверждения.

## Каталог и панели

Центральный `LociTypeDetector` распознаёт `Penta_D → Penta D`, `Penta_E → Penta E`, `VWA → vWA`. Правило Penta применяется и вне NGS-конвертера.

Первые восемь новых STR были явно перечислены в задании: `AC001348B`, `D10S1237`, `D11S1304`, `D12S1064`, `D21S1446`, `D22S684`, `GATA23B10`, `GATA83B04`. После проверки реального файла добавлены ещё 39 STR (полный перечень ниже). Все 47 доступны панелям, обычному импорту и динамическим колонкам анализа. Неизвестные имена вида `D…S…` автоматически в каталог не добавляются.

NGS-предпросмотр составляет полный отчёт по уникальным исходным названиям каждого загруженного файла. Этот отчёт служит основанием для дальнейшего расширения каталога после проверки неизвестных маркеров. Состав официальной коммерческой панели не выводится из суффикса `ASTR+`.

Экспорт сначала размещает локусы выбранных панелей, затем остальные локусы источников в их порядке, затем пустые колонки общего каталога. Дополнительные локусы не удаляются, расхождения с панелью показываются. Метаданные различают каталог и реально исследованные локусы, поэтому пустые добавленные колонки не повышают полноту профиля.

## XLSX и диагностика

Готовый файл содержит только один лист **Импорт**, с колонками `Объект`, `Год` и локусами. Листы «Проверка», «NGS QC» и `_DNA_META` не создаются, в том числе скрытыми. Диагностика NGS и решения остаются доступными в интерфейсе конвертера; в готовый файл и далее в БД через этот файл они не переносятся.

Половые локусы (AMEL, SRY, X/Y-маркеры и Y-InDel) находятся в конце. Скрытие пустых столбцов действует и для NGS, а порядок внутри групп сохраняется. Имя файла образуется по номеру экспертизы из объектов и году: `250-1`, `250-2`, 2026 → `250-2026.xlsx`. Правила нескольких экспертиз и годов описаны в [инструкции конвертера](GENETIC_EXCEL_CONVERTER.md).

Файл проходит стандартный импорт с сохранением принятых аллелей. Панель при необходимости выберите при загрузке. Старые книги со скрытыми метаданными продолжают импортироваться.

Ограничения источников: до 100 файлов, 10 МиБ каждый, 50 МиБ всего; 20 000 строк и 512 колонок на лист; настройки до 2 МиБ. Для транспонированного NGS действует предел 510 маркеров на файл.

Неизменяемый разбор NGS кэшируется в памяти сервиса по SHA-256 содержимого и параметрам источника: до 100 записей / 64 МиБ / 5 минут. При изменении решения повторно используется промежуточная модель. Решения, панели и референсы пересчитываются отдельно. Каждый запрос передаёт оригинальные файлы и проходит авторизацию.

## API

Используются существующие POST `/api/genetic-excel-converter/preview` и `/export`, multipart `files` + `options`, Bearer-токен и `X-Active-Department-Id`.

Сначала получите `file.id` и `record.cell.id` из preview. Затем передайте настройки с теми же файлами в том же порядке:

```json
{
  "files": {
    "<file.id>": {
      "objectNumber": "251-3",
      "objectConfirmed": true,
      "year": 2026,
      "panelId": "<необязательный UUID панели>"
    }
  },
  "cells": {
    "<record.cell.id>": {
      "action": "manual",
      "value": "16,18",
      "reason": "Подтверждено экспертом после проверки Detail",
      "timestamp": "2026-10-13T08:00:00.000Z"
    }
  }
}
```

NGS-данные preview находятся в `files[].ngs.records`, отчёт по каталогу — в `files[].ngs.locusReport`. Нерешённые условия отражаются в общем `issues`, `canImport` и `canUpload`. Export повторно проверяет данные на сервере и возвращает HTTP 409, если остаётся блокирующая ошибка.

### Проверка реального образца

Проверен приложенный `r2.251-3_20260714.ASTR+.xlsx`: листы Result и Detail, 113 строк Result (111 ASTR + 2 SEXUAL), 233 строки Detail. После объединения AMELX/AMELY получается 112 канонических локусов.

Полный перечень 111 исходных ASTR-названий находится в `tests/fixtures/ngs-astr-marker-names.js`. Там нет генотипов, QC или последовательностей пользователя; тестовые генотипы генерируются синтетически. Историческая классификация SE33 как OTHER сохранена.

На реальном файле проверены TH01, D18S51, D19S433, D21S11, D5S818, Penta_D, Penta_E, VWA и оба сигнала AMEL. Микроварианты сохраняются; дополнительные аллели и последовательностные варианты не отбрасываются; D19S433 с отсутствующим генотипом и Failed/Low Coverage остаётся пустым. Пустые QC-флаги Result не считаются Pass, даже если Detail содержит Pass: требуется явная проверка.

В образце после объединения AMEL: 23 локуса с одной аллелью, 82 с двумя, 6 с более чем двумя, 1 без результата. Это статистика исходных значений, а не экспертная интерпретация смеси или гомозиготности.

Интеграционная проверка реального файла прошла через HTTP preview → запрет export до решений → export XLSX → обычный preview импорта → upload → PostgreSQL. Для этой проверки использованы **технические решения**: сохранить исходные наборы, для одиночных STR обозначить неизвестную вторую аллель. Эти решения не являются экспертным заключением и не применялись к рабочей БД. Проверены массивы аллелей всех локусов, год, задача, панель и сохранность принятых аллелей. Исходные строки Result/Detail доступны в предпросмотре, но после удаления служебного листа не экспортируются. Проверочная БД изолирована от рабочей.

Запуск проверки с частным образцом (файл не включается в Git):

```bash
NGS_TEST_DATABASE_URL='postgres://.../dna_ngs_test' \
NGS_REAL_SAMPLE_PATH='/absolute/path/to/private-sample.xlsx' \
node --test tests/ngs-astr-import.integration.test.js
```

Без `NGS_REAL_SAMPLE_PATH` выполняется синтетический сценарий; без `NGS_TEST_DATABASE_URL` интеграционный тест пропускается. Принятие смесей, одиночных аллелей, спорного AMEL и sequence-вариантов остаётся решением пользователя.
