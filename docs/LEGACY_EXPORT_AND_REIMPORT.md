# Выгрузка старых данных, переход и откат

## До production-изменений

Сначала read-only preflight. В текущем контейнере можно выполнить
`node scripts/workspace-preflight.js`; для host-запуска нужен доступный DATABASE_URL,
не выводите его в журнал. Скрипт читает агрегаты внутри READ ONLY транзакции:
число профилей/пустых/отсутствующих лет, отделений, организаций и коллизий старого ключа.
Реальные генотипы, ФИО, пароли и ключи не печатаются.

В приложении: **Система → Выгрузка для переноса** (`/admin/migration-export`).
Доступ — admin/system_administrator в своей организации. Выбор источников,
нескольких лет и старых отделений — чекбоксами, с отдельными пунктами отсутствующих
значений. Внутри группы OR, между группами AND. Пустой выбор означает ноль строк.
Фильтр использует сохранённый год профиля. Старый staff без достоверного № рег./года
выгружается с пустыми полями, без выдуманных значений. Строковое подразделение staff
не приравнивается к department UUID.

Предпросмотр показывает реальные количества по источникам/годам/отделам,
пустым и недостающим метаданным. Файл создаётся общим генератором V2.
Генотипы не загружаются в DOM для выбора; PostgreSQL cursor читает пачками 500
в согласованной REPEATABLE READ READ ONLY транзакции. Один XLSX содержит до 10000
строк (либо меньшую часть по объёму ячеек). Большая выборка превращается в ZIP
с полноценными XLSX и реестром, без отбрасывания хвоста. Fingerprint предотвращает
скачивание изменившейся с момента preview выборки без повторной проверки.
HTTP-выгрузка складывает части в закрытый временный каталог `runtime/exports`
(в контейнере `/app/exports`), затем передаёт один XLSX или потоковый ZIP. Права
каталога 0700, файлов 0600; завершение, отмена и ошибка удаляют временные части.
В памяти не накапливается вся выгрузка из нескольких XLSX.
Экспорт/скачивание аудитируются без генотипов/ФИО в журнале.

**XLSX не является резервной копией приложения.** Старые задачи, история,
снимки IDENT/TRIO, отчёты и связи требуют сохранения БД и файлового хранилища.

## Отдельный стенд

1. Сохраните SQL-дамп, `.env`, `config/encryption.key`, uploads/exports и ID старого образа.
2. Проверьте восстановление на отдельной БД. Для интеграционных тестов имя должно
   начинаться с `dna_workspace_test_`; используйте синтетические данные.
3. Поднимите отдельный Compose project с иными container_name/свободными портами
   и bind mounts **внутри папки стенда**. Не направляйте его на production volumes.
4. Примените `database/migrations/037_personal_workspace.sql` к БД стенда.
   Миграция добавочная, повторяемая; не назначает УГ/год всей истории, не удаляет профили.
5. На стенде включите `workspace_configuration.enabled=true` и
   `UNIFIED_WORKSPACE_ENABLED=true` у web. Оба условия обязательны; несогласованная
   конфигурация останавливает старт, вместо смешения frontend/backend схем.
6. Загрузите выбранные XLSX-части; задайте категории, годы и данные сотрудников.
   Новые UUID создаются сервером. Подтвердите импорт в личный массив.
7. Сверьте число строк/аллели/микроварианты/спецтокены, пустые и provenance.
   Запустите полный поиск, проверьте публикацию/контаминацию и IDENT/TRIO.

Опциональный помощник `WORKSPACE_DATABASE_NAME=dna_workspace_test_... ./scripts/workspace-cutover.sh --staging`
работает только с тестовым именем БД. Запускайте в проекте стенда с его Compose.
Он собирает `dna_database-web:workspace-candidate`, сохраняет защищённые копии,
применяет схему и включает её в указанной тестовой БД. Production web не перезапускается.

## Согласованное переключение production

Наличие этой инструкции не означает, что переключение уже выполнено. По ТЗ
production-миграции требуют отдельного согласованного запуска после проверок.
До переключения обычный `update_server.sh` намеренно останавливается на неизвестной
миграции 037; повторный запуск обновления не является подтверждением перехода.

После утверждения и окна обслуживания, из подготовленного checkout релиза:

```bash
./scripts/workspace-cutover.sh --confirm-production-cutover
```

Скрипт сначала собирает web с обязательными checks/tests/build; сохраняет SQL,
конфигурацию, ключ и uploads/exports в закрытую папку `runtime/backups/workspace_*`.
Затем останавливает web, делает **окончательный** SQL-дамп после прекращения записей,
применяет 037, включает DB/config и только свой web. Порт 3000 хоста не используется;
существующие WEB_BIND_IP/WEB_PORT, БД, Redis и прочие проекты не меняются.
Составьте план переноса изменений между первичной выгрузкой и этим финальным дампом.

Не импортируйте весь экспорт обратно в ту же действующую БД без плана коллизий.
Основной перенос — отдельная новая установка/БД и явное сопоставление. Для обновления
существующего опубликованного объекта есть отдельное подтверждение с повторной
серверной проверкой типа/года/номера и полного поиска; файл сам по себе не разрешает overwrite.

Старые мастер-массивы читаются совместно как эталоны организации. Новые обычные
публикации идут в один organization_default array. Существующие сотрудники продолжают
использоваться. Рабочая копия ещё не эталон. Удаление рабочей копии не удаляет публикацию.

## Откат

- Прекратите новые записи. Сохраните проблемную БД/новые записи отдельно для разбора.
- Восстановите **финальный pre-cutover dump в отдельную БД**, проверьте число строк,
  историю и контрольные суммы; не очищайте исходную единственную БД.
- Используйте соответствующие `.env`, исходный ключ и файловый архив из той же точки.
- Подключите сохранённый старый образ (`previous-image-id.txt`) к восстановленной
  старой схеме; UNIFIED_WORKSPACE_ENABLED должен быть выключен.
- Проверьте вход, поиск/экспорт, историю и доступ DNAEXCEL до переключения адреса.
- Сохраните новую/старую БД и архивы до завершения сверки.

Возврат только старого web поверх изменённой схемы не считается проверенным откатом.
Запрещены down -v, prune volumes и автоматическое удаление старых таблиц/томов.

## Проверено в этой реализации

Отдельная синтетическая БД: повторная миграция; миграция заполненной старой схемы
с сохранением контрольных сумм генотипов/номеров; восстановление pre-migration dump
в другую БД с прежней схемой. Unit/integration/API/UI сценарии и точные итоговые
числа проверок фиксируются в журнале реализации/PR. Нативная научная валидация
математических моделей этим техническим переходом не подменяется.
